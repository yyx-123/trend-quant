## 1. R8（中）：`superseded_by` 的落点与 append-only 冲突

**位置**：详设 §6.3 `research_verdicts` 表尾（R3 刚加的字段）与 §6.6.7
重跑运动段。

**现状原文（§6.3，R3 新增）**：

```
  suggested_verdict, final_verdict, reasoning,
  holdout_touched, attempt_index_snapshot,
  superseded_by(可空：复核 verdict 的 experiment_id / verdict_id，
                见 §6.6.7 重跑运动；append-only，旧记录不改不删)
```

**现状原文（§6.6.7）**：

```
模块升级（如 `chandelier@1 → @2`）后，平台可发起**重跑运动**
（recompute campaign）：批量重跑引用旧模块版本的历史实验，产出新
verdict。台账 append-only 不破：旧 verdict 不改不删，新复核 verdict 通过
`superseded_by` 指针链接（旧记录标 superseded、指向新记录）——
"这个结论当时凭什么成立"与"模块修正后它还成不成立"都可查。
```

**问题（两处）**：

1. **语义自相矛盾**：字段名 `superseded_by`（"被谁取代"）写在 verdict 行上，
   逻辑上属于**旧记录**——但旧记录要写这个字段就得 UPDATE，直接违反
   §6.7 的 append-only（各表只有 insert/select + 触发器拒 UPDATE/DELETE）；
   §6.6.7 自己也写着"旧记录不改不删"，却又说"旧记录标 superseded"；
2. **字段口径含糊**：注释写"复核 verdict 的 experiment_id / verdict_id"，
   两个候选没有定论；而 `research_verdicts` 在 §6.3 里以 `experiment_id`
   为键，没有独立 `verdict_id` 定义。

**改法（append-only 安全的最小方案：指针放在新记录上）**：

**位置 1** — §6.3 表尾字段改写：

```
  suggested_verdict, final_verdict, reasoning,
  holdout_touched, attempt_index_snapshot,
  supersedes(可空：本 verdict 是复核产物时，指向被复核的旧 verdict 的
             experiment_id；append-only——指针只写在新记录上，旧记录
             永不改动，"谁被取代"由反向查询得出，见 §6.6.7)
```

**位置 2** — §6.6.7 按新语义改写末段：

```
（recompute campaign）……台账 append-only 不破：旧 verdict 一行不改。**指针
只写在新记录上**——新复核 verdict 的 `supersedes` 字段指向被复核的旧
verdict（experiment_id）；"谁已被取代"由台账反向查询（`supersedes = X`
的新记录存在与否）得出，无需回写旧行。旧行加一个查询期标记
（superseded 视图，非存储字段）供看板折叠显示。
```

**验收**：

- 全文 `superseded_by` 为 **0 处**，`supersedes` 出现 2 处（§6.3、§6.6.7），
  语义一致："新记录指向旧记录"；
- §6.6.7 不再出现"旧记录标 superseded"这类需要 UPDATE 的表述；
- 与 §6.7 append-only 规则无冲突（指针只在新行）。
