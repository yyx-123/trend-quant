## 1. 包结构与依赖约束

新增/演化的顶层包（与架构稿分层一一对应）：

```
src/
  data/          # L1 数据层（现有，增量演化）
  gateway/       # L1.5 数据门面层（新建）
  engine/        # L2 交易引擎层（新建，纯执行）
  portfolio/     # L3 组合策略层（新建）
  research/      # L4 投研层（新建）

  rule_backtest/ # 并行分支：单标的/批量回测（保留，非核心迭代方向）
  services/      # 展示/应用分支的应用服务（保留）
  app/           # 展示/应用分支的 Web 层（保留）
```

依赖规则（架构稿决策 7、10）：

- 执行面：`research → portfolio → engine`，只能调直接下一层；
- 数据面：`engine / portfolio / research` 取数只能经 `gateway`；`gateway` 只能调
  `data`；**禁止任何层绕过 gateway 直连 data 的行情读取**；
- `rule_backtest` 与 `services` 属并行分支，维持现状依赖（直读 data），不受新
  规则约束，但新代码不得从研究栈反向依赖它们（只允许单向打捞：如 risk_budget
  数学、费用常量迁入新栈后，旧分支继续用自己的副本直至自然退役）；
- 落地手段：包级 import 约定 + code review 卡控；`core/`（指标、日历、符号等
  纯计算）继续作为全项目共享的单一实现地，任何层可用（它无状态、不读库）；
- **共用件的归属**（2026-09-23 明确）：指标**计算**是纯函数 → `core/`（横切
  共享库，不属于 L1-L4 任何一层，如同 numpy）；**已算好的生产指标缓存值的
  读取** → L1 存、L1.5 透传（这是"数据"）；**费用常量**是 A 股交易规则参数 →
  L2 `engine/fees.py`。L1.5 只装"带语义的数据读取"，不当计算库。

## 2. L1 数据层：增量改造

现状保留（架构稿 §1.1 已有机制不重做）：raw 真源 + qfq 物化、data_versions、
indicator_daily/trend_daily 缓存、日更调度、盘中快照。

新增一项能力：

**面板批量读取**（供 gateway 调用）：

```
load_panel(symbols, start, end, fields, adjust) -> Panel
  fields ⊂ {open, high, low, close, volume, amount, pre_close}
  adjust = "raw" | "qfq"          # 绝对价格判断用 raw，收益/指标计算用 qfq
  返回：按 (date, symbol) 对齐的内存面板（pandas/numpy）
```

- 现有 `load_market_data_many` 是雏形，需补齐：pre_close（涨跌停推导用）、
  amount（成交额，龙头池/流动性过滤用）、字段级选择（避免整行载入）；
- as-of 语义**不在 L1 实现**——L1 是无脑存储，as-of 卡控是 gateway 的职责
  （决策 10：语义全系统只在 L1.5 实现一处）。

元数据补充（随数据线阶段 7 推进，非主线）：上市/退市日期（激活
`instrument_metadata.start_date` 消费）、ST 状态历史、成交额/市值历史、
指数成分历史。**任何新数据项的透出链路固定为：L1 先存 → L1.5 元数据接口
透出 → 上层消费**（universe 过滤、涨跌停 ST±5% 推导、时点池等）——上层
永远不直连 L1。

## 3. L1.5 数据门面层（gateway 包）

全系统唯一数据咽喉。模块划分：

```
gateway/
  panel.py        # 面板读取（as-of 强制）
  tradability.py  # 可交易性标注（涨跌停/停牌推导）
  metadata.py     # 日历、行业、上市日期、股票池成员
  audit.py        # 数据请求留痕
```

### 3.1 面板读取（as-of 强制）

```
get_panel(request) -> Panel
request:
  symbols, start, end, fields, adjust,
  as_of: datetime            # 必填，调用方声明的决策时刻
  mode: "historical" | "live"
```

强制规则：

- `as_of` 必填，无默认值——调用方必须显式声明"我站在哪个时刻做决策"；
- `historical` 模式：返回数据严格 ≤ as_of；盘中合成 bar、provisional 标记一律
  不出现（周/月 provisional bar 由 `core/bars.is_period_bar_provisional` 过滤）；
- `live` 模式（仅供实盘运行器）：允许含截至 as_of 的盘中合成 bar（复用
  `intraday_service` 的合成逻辑），返回面板上带 `provisional` 标记列；
- 每次调用留痕（§3.3）。

### 3.2 可交易性标注

```
get_tradability(symbols, dates) -> DataFrame
  每行: (date, symbol) -> {suspended, limit_up_price, limit_down_price,
                           is_limit_up(收盘≥涨停), is_limit_down(收盘≤跌停)}
```

推导规则（不需要额外数据源）：

- 停牌：`tradability` 日无 bar 且当日是交易日 → suspended=True；
- 涨跌停价：由 raw pre_close 按板块规则推导——
  - 主板（.SS 60xxxx、.SZ 00xxxx）±10%；
  - 科创板（.SS 68xxxx）、创业板（.SZ 30xxxx）±20%；
  - ST ±5%（依赖 ST 状态元数据，阶段 7 前无此数据 → 标记 unknown 并按主板
    规则处理，报告注明）；
  - 新股上市初期无涨跌幅限制（依赖上市日期元数据，同上）；
  - 价格按分（0.01）四舍五入；
- 一字板近似：`is_limit_up` 用收盘价判定（尾盘口径下，收盘封板 ≈ 尾盘不可买，
  与决策 1 的口径自洽）。

### 3.3 请求留痕（audit）

每次 `get_panel`/`get_tradability` 调用写一行审计记录（异步、批量落库）：
调用层（engine/portfolio/research）、run_id（若有）、as_of、符号数、日期范围、
data_version。用途：实验血缘（该回测当时看到的是哪一版数据）、PIT 审计复查。

## 4. L2 交易引擎层（engine 包，纯执行）

### 4.0 与现有 rule_backtest 引擎的关系（先答清楚）

**全新一套，不在旧引擎上迭代。** 旧引擎（`src/rule_backtest/`）保留给单标的/
批量回测分支继续运行（并行分支，非核心迭代方向）；新 L2 引擎是组合级、
纯执行的新实现。两者共享的只有 `core` 指标计算与费用常量（迁入
`engine/fees` 后旧分支自留副本）；止损"收编"= 新栈统一实现
（`engine/stops.py`），旧两份实现（`state_values.py`、`stop_loss.py`）不动，
随各自分支自然演化或退役。

```
engine/
  models.py       # Order/Fill/Position/Account（下述）
  matcher.py      # 撮合：尾盘模型 + 止损触发 + 卡控
  fees.py         # 费用（印花税/佣金/最低5元/滑点/尾盘滑点）
  stops.py        # 止损原语（收编双实现）
  account.py      # 账户记账、T+1 可卖管理、组合热
  store.py        # 运行状态与成交流水落库
```

### 4.1 存储表（新增）：每张表干什么 + 具体存什么

**层级关系**：一次回测/实盘运行 = 一行 `engine_runs`（一个 run_id）；
其余各表全部是这个 run_id 的子记录——一次回测产生成百上千行
orders/fills、每个持仓每天一行 positions、每个交易日一行 daily_nav。

```
engine_runs         # 运行档案：run_id, kind(backtest|live), strategy_ref,
                    #   config_hash, resolved_config_yaml(解析后完整配置,
                    #   保证实验期策略可复现), data_version, engine_version,
                    #   git_hash, started_at, finished_at, status
engine_orders       # run_id, order_id, decision_date, target_fill_date,
                    #   symbol, side, intent_type, intent_value, source, status
engine_fills        # run_id, order_id, symbol, fill_date, base_price,
                    #   slippage_base, slippage_tail, fill_price, quantity,
                    #   commission, stamp_tax, fee_total, cash_after
engine_unfilled     # run_id, order_id, symbol, decision_date, reason
                    #   (limit_up|limit_down|suspended|t1_block|
                    #    insufficient_cash|lot_rounding), intent_snapshot
engine_positions    # run_id, date, symbol, quantity, sellable_quantity,
                    #   avg_cost, entry_date, entry_price, stop_price,
                    #   highest_since_buy, atr_at_entry,
                    #   module_state(持仓风控模块自定义状态，见 §4.3.1)
                    #   （逐日快照）
engine_daily_nav    # run_id, date, cash, positions_value, equity, heat, exposure
```

逐表说明与实例：

- **`engine_runs` 运行档案**——一次回测或一次实盘运行的"身份证"：谁跑的
  （哪个策略）、用的什么配置、基于哪版数据和代码。它是血缘锚点。
  例：`{run_id: R20240901-031, kind: backtest, strategy: base-v1@3,
  config_hash: 9f2c…, resolved_config_yaml: <完整七槽 YAML>, data_version: 418,
  engine_version: 1.0.0, git_hash: a1c78…, started_at: 2026-09-23 10:00,
  finished_at: 2026-09-23 10:02, status: finished}`
- **`engine_orders` 订单（决策意图）**——策略"想做什么"，决策日与成交日
  分列（尾盘口径的审计需要）。
  例：`{order_id: O-8812, decision_date: 2024-03-15, target_fill_date:
  2024-03-15, symbol: 510500.SS, side: buy, intent_type: quantity,
  intent_value: 4600, source: signal, status: filled}`
- **`engine_fills` 成交（事实）**——实际成交价格、数量、费用分列。
  例：`{order_id: O-8812, fill_date: 2024-03-15, base_price: 5.82,
  slippage_base: 0.002, slippage_tail: 0.001, fill_price: 5.837,
  quantity: 4600, commission: 5.00（万 0.854 不足 5 元按 5 元）,
  stamp_tax: 0.00（买入不收）, fee_total: 5.00, cash_after: 23150.4}`
- **`engine_unfilled` 未成交记录**——"想买买不到"的订单（"错过的交易"
  本身是研究素材，故独立成表而非 fills 里的空行）。
  例：`{order_id: O-8857, decision_date: 2024-04-02, symbol: 159915.SZ,
  reason: limit_up, intent_snapshot: {quantity: 3000, rank_score: 0.83}}`
- **`engine_positions` 持仓逐日快照**——每个持仓每天的状态：数量、
  **可卖数量（T+1 一等表达）**、成本、止损价、买入以来最高价。
  例：`{date: 2024-03-15, symbol: 510500.SS, quantity: 4600,
  sellable_quantity: 0（当日买入，T+1 不可卖）, avg_cost: 5.838,
  entry_date: 2024-03-15, entry_price: 5.837, stop_price: 5.53,
  highest_since_buy: 5.90, atr_at_entry: 0.12}`
- **`engine_daily_nav` 组合逐日结算**——账户每天收盘后的总账：现金、
  持仓市值、净值、组合热、仓位。
  例：`{date: 2024-03-15, cash: 23150.4, positions_value: 268400,
  equity: 291550, heat: 0.031, exposure: 0.92}`

### 4.2 撮合语义（尾盘执行模型，决策 1）

单笔买入订单的生命周期（决策日 t 生成）：

1. **卡控**（查 gateway 可交易性标注）：
   - t 日 suspended → unfilled(suspended)；
   - t 日收盘 is_limit_up → unfilled(limit_up)（尾盘封板 ≈ 买不到）；
2. **定量**：整手 100 对齐（卖出全清例外）；现金校验（含预估费用）不足 →
   逐手递减，递减到 0 → unfilled(insufficient_cash / lot_rounding)；
3. **成交**：fill_price = close(t) × (1 + 基础滑点 + 尾盘滑点)（买入为正、
   卖出为负）；费用分列（佣金双边万 0.854 最低 5 元；印花税卖出 0.05%
   仅股票）；
4. **T+1**：当日买入计入 quantity、不计入 sellable_quantity；卖出校验
   sellable_quantity，当日新买部分想卖 → unfilled(t1_block)。

卖出订单（策略信号卖出）同上，is_limit_down → unfilled(limit_down)。

**止损触发**（position_risk 槽下达的止损单，引擎按盘中语义执行）：

- 盘中触及：`low(t) ≤ stop_price` → 按 stop_price 成交；
- 跳空穿透：`open(t) < stop_price` → 按 open(t) 成交（沿用现有
  stop_gap_fill 语义）；
- 触发日跌停：`low ≤ stop 且 is_limit_down` → 当日不可卖，
  unfilled(limit_down)，次一交易日重试（这是 A 股止损缺口的诚实建模，
  现有引擎缺失）。

### 4.3 止损原语收编（决策 6）：执行语义归引擎，公式可插拔

职责切分：**引擎（stops.py）只负责止损的执行语义**（盘中触及按止损价
成交、跳空按开盘、跌停顺延重试，见 §4.2）；**止损公式本身是可插拔模块**
（L3 `position_risk` 槽），首批内置四个：硬止损（hard_stop）、吊灯
（chandelier）、棘轮吊灯（ratchet）、时间止损（time_stop，持有 N 日强制
离场）。新公式 = 注册新模块，引擎无需改动。

统一口径（决策 6）：以**实际买入价**为基准、**ATR 含当根**（与现行实盘侧
`stop_loss.py` 一致，回测侧向实盘侧对齐）：

- 硬止损 = entry_price − atr_mul × ATR(20)；
- 吊灯 = highest_since_buy − atr_mul × ATR；棘轮变体只上移；
- 旧两份实现（`rule_backtest/state_values.py`、`services/stop_loss.py`）不动
  （并行分支）；`stop_loss.py` 的实盘守护后续切到 engine 实现（随实盘
  运行器落地）。

### 4.3.1 业界常见止损策略的表达力验证（2026-09-23 调研）

对照业界通行止损族（MQL5 交易管理器六类、Volatility Box 对照回测、
文华/期货止损十法等）逐一试装：

| 止损策略 | 公式 | 适配方式 | 结论 |
|---|---|---|---|
| 固定百分比 | entry × (1−p) | 模块一行公式 | ✅ 内置 |
| ATR 硬止损 | entry − k×ATR | 已有 | ✅ 内置 |
| 吊灯 / 棘轮 | 最高 high − k×ATR（棘轮只上移） | 已有 | ✅ 内置 |
| **均线止损（MA20/MA40）** | 收盘跌破 MA → 离场 | stop = MA 值，**收盘确认型**离场（见协议补强②） | ✅ 内置首批 |
| 抛物线 SAR | 加速因子递推 | 需自定义状态（af/极值点）→ 协议补强① | ✅ 协议补强后 |
| Supertrend | ATR 带 + 方向翻转 | 需自定义状态（方向位）→ 协议补强① | ✅ 协议补强后 |
| 唐奇安/前低止损 | min(low, N)（海龟出场） | 经 gateway 取窗口即可 | ✅ |
| 百分比回撤 trailing | 持仓以来最高价 × (1−p) | 吊灯同构（换距离定义） | ✅ |
| 保本止损 | 浮盈 > 1×ATR 后止损上移至成本价 | 需 1-bit "已激活"状态 → 协议补强① | ✅ 协议补强后 |
| 阶梯式 step trailing | 每涨 X 上一档 | 自定义状态 | ✅ 协议补强后 |
| 波动率带（Keltner/BOLL 下轨） | 跌破带下轨离场 | 经 gateway 取数算带 | ✅ |
| 时间止损 | 持有 N 日强制离场 | 已有 | ✅ 内置首批 |
| 止盈/盈利目标 | 达 R 倍数/目标价离场 | position_risk 同样管止盈（evaluate 产出售出意图） | ✅ |

**两处协议补强**（调研发现的真缺口）：

1. **StopState 支持模块自定义状态**：PSAR 的加速因子、Supertrend 的方向位、
   保本止损的激活位都不是固定字段装得下的——`StopState` 增加不透明
   `module_state: dict`（随 engine_positions 逐日快照落库，键值由模块自定义），
   固定字段（stop_price/highest_since_buy/atr_at_entry）仍保留为公共部分；
2. **两种离场语义并存**：盘中触及型（模块给出 stop_price，引擎盘中盯守，
   触及即成交——吊灯/硬止损这类）与**收盘确认型**（模块每日 evaluate 判断
   条件，成立则尾盘卖出——均线止损这类"收盘跌破才算"的语义）。
   `ExitOrderIntent` 带 `fill_mode: intraday_stop | tail` 字段区分。

附带一个 heat 口径说明：组合热（§4.4）对带显式 stop_price 的持仓精确计算；
收盘确认型持仓（无固定止损价）用其当日参考线（如 MA20 现值）作为近似
止损价计入 heat——近似即可，heat 本是风控预算不是精确预测。

### 4.4 账户与组合热

`account.py` 逐日结算：cash/positions_value/equity（收盘估值）、exposure、
**portfolio_heat** = Σ max(0, (现价 − stop_price) × quantity)。heat 为无止损
持仓记 None 并告警（组合热的前提是每个持仓有止损）。**空仓资金按
cash_yield 参数计息**（默认货基/逆回购利率，业界 NAV 惯例，2026-09-22
审计 A 项接纳；设 0 即退回零收益旧口径）、无融资。

**组合热算例**：权益 291,550 元，持三仓：

```
A: 现价 12.0, 止损 11.4, 3000 股 → (12.0−11.4)×3000 = 1,800
B: 现价 25.0, 止损 26.0, 1000 股 → max(0, …) = 0（止损价高于现价，
   潜在盈利不计入热）
C: 现价 8.0,  止损 7.4, 5000 股 → (8.0−7.4)×5000 = 3,000
heat = 4,800 元 = 权益的 1.65%
```

含义：若 `heat_cap = 6%`，则当日新买入最多还能增加 17,493 − 4,800
≈ 1.27 万元的"到止损潜在亏损"额度；超出的候选被 portfolio_risk 拦截
（拦截原因落 run 日志）。

**三层概念别混**：`risk_budget_pct`（sizing 槽）是**单笔**风险预算——
这一笔最多亏权益的 0.75%；`heat` 是**存量**度量——现在所有持仓明天
全被打止损一共亏多少；`heat_cap`（portfolio_risk 槽）是**组合总量上限**
——heat ≤ 权益 × 6%。组合热 = 组合整体风险敞口的存量度量，heat_cap
是它的预算上限。

## 5. L3 组合策略层（portfolio 包）

> 依赖：只调 L2（engine）与 L1.5（gateway）；被 L4（research）调用。

### 5.1 模块构成

### 5.2 插槽协议

所有插槽共享一个上下文对象（`context.py`）：

```
DayContext:
  date                 # 当日 t
  as_of                # = t 收盘（尾盘口径，决策 1）
  gateway              # L1.5 句柄（as_of 已绑定，模块拿不到未来数据）
  account              # L2 账户只读视图（cash/equity/heat/positions）
  params               # 本插槽的参数（来自策略配置，已过 schema 校验）
  data_version         # 血缘
```

模块拿数据的唯一途径是 `ctx.gateway`——PIT 卡控因此不需要模块自觉。

#### 5.2.0 模块长什么样（四个具体例子）

- signal 模块 `ma_cross@1`：读收盘价序列，算 MA20；今天收盘 > MA20
  且昨天 ≤ MA20 → 发一个"买入候选"事件（反向发"卖出"事件）。
  参数：n=20（均线天数）；
- rank 模块 `by_freshness@1`：把今天的候选按"信号几天前出现"排序，
  越新越靠前。无参数；
- sizing 模块 `equal_risk@1`：每只买入数量 =（总资产 × 0.75%）÷
  （预估买入价 − 预估止损价）——亏到止损时正好亏总资产的 0.75%。
  参数：risk_budget_pct=0.0075；
- position_risk 模块 `chandelier@1`：每天收盘后算"买入以来最高价 −
  2.5×ATR"，收盘跌破 → 卖出。参数：atr_mul=2.5。

#### 5.2.1 `universe` 标的池

```
protocol UniverseProvider:
    def members(self, ctx) -> list[UniverseMember]
UniverseMember: {symbol, category_l1/l2/l3, asset_type}
```

- 返回成员需带类目（组合风控的集中度卡控要用）；
- 内置实现：`static_list`（显式清单）、`category_filter`（三级类目+enabled+
  **asset_type**：只做 ETF / 只做股票 = 一个参数的事）、`liquidity_filter`
  （近 N 日成交额 ≥ 阈值——等风险世界里的"可交易池"）；
- **规模**：子集到全量标的池均可。千级~几千候选在工程上可行——量级账：
  2500 标的 × 20 年日 K ≈ 1250 万行，面板载入内存约数百 MB（字段级选择 +
  float32 可再压缩）；信号计算走 (T,K) numpy 向量化（现有 `rolling_bars`
  已在 874 标的上验证同构路径），逐日引擎循环的事件部分天然稀疏
  （只有成交日有订单）。瓶颈不在计算，而在数据覆盖——当前库 874 只，
  扩到几千只是数据线（阶段 7）的事；
- 提醒：大池子的价值主要在**研究样本量**（event/bucket 的统计效力）；
  实盘策略的候选需求其实很小（组合构建调研实证：事件口径下候选
  ~12 只/日、持仓 15–20 只即优）——池子可以大，但别以为池子大策略就好；
- 后期（数据线）：`yearly_leaders`（年度龙头动态池，架构稿决策 2）。

#### 5.2.2 `signal` 信号

```
protocol SignalModule:
    def scan(self, ctx, members) -> list[SignalEvent]
SignalEvent: {symbol, kind: "entry"|"exit", date, meta: dict}
```

- 输出是**事件流**（架构稿：候选口径用"事件"不用"状态"）；entry=建议买入，
  exit=建议卖出（持仓风控之外的策略性离场）；
- 内置实现：`macd_cross`（金叉 entry/死叉 exit，经 gateway 取 close 序列用
  core.indicators 计算）、`trend_score_cross`（趋势值上/下穿阈值）；
- 信号模块**不决定买不买、买多少**——它只生产候选。同日同标的重复事件由
  回测器去重（已持仓的 entry 忽略，未持仓的 exit 忽略）；
- exit 事件与 position_risk 的关系：exit 是"策略认为趋势结束"，position_risk
  是"风控认为该止损"——两者并列，任一触发即卖（现行实盘语义）。

#### 5.2.3 `rank` 排序

```
protocol RankModule:
    def rank(self, ctx, candidates: list[SignalEvent]) -> list[SignalEvent]
```

- 纯排序（返回重排后的候选序列），不做筛选——筛选是 portfolio_risk 的职责
  （单一职责：rank 管"谁先谁后"，portfolio_risk 管"谁进谁出"）；
- 内置实现：`by_freshness`（事件发生后天数升序，默认）、`by_er`（ER 降序）、
  `random`（合法默认！猴子基准）、`composite`（多键加权，实验素材）；
- 排序键需要的特征（freshness、ER 等）由 signal 事件 meta 携带或经 gateway
  现算，接口上 rank 只看到 ctx + candidates。

#### 5.2.4 `sizing` 仓位

```
protocol SizingModule:
    def size(self, ctx, candidate, stop_price) -> OrderIntent | None
OrderIntent: {symbol, side:"buy", intent_type:"quantity"|"target_value", value}
```

- 输入含 `stop_price`（由 position_risk 槽预估的拟止损价）——等风险的数学
  依赖止损距离，这是 sizing 与 position_risk 唯一的接口接触点；
- 内置实现：
  - `equal_risk`（**打捞自 risk_budget**：数量 = 风险预算额 ÷ (买入预估价 −
    stop_price)，预算额 = equity × risk_budget_pct；整手与现金裁量归引擎）；
  - `fixed_pct`（equity × pct 定额）、`fixed_slots`（equity ÷ 槽位数均分）；
- 返回 None = 放弃本候选（如止损距离 ≤ 0）； sizing 不做资金池分配——
  够不够钱是引擎和 portfolio_risk 的事。

#### 5.2.5 `portfolio_risk` 组合风控

```
protocol PortfolioRiskModule:
    def admit(self, ctx, intents: list[OrderIntent],
              pending_exits: list[str]) -> list[OrderIntent]
```

- 对"排序 + 定量后的买入意图清单"做总风险卡控，返回放行清单（可截断、
  可调量，不调序——调序是 rank 的事）；
- 内置实现（可叠加，配置里按序应用）：
  - `slot_limit`：持仓数 ≤ N（考虑 pending_exits 释放的槽位）；
  - `heat_cap`：加入后组合 heat ≤ equity × 上限（heat 由引擎账户提供）；
  - `concentration_cap`：同 category_l2 持仓 ≤ M（成员类目来自 universe）；
  - `market_gate`：breadth（universe 内站上 SMA200 比例）处于中段时，
    风险预算减半或暂停新开仓（ex-ante 闸门，实验素材）；
  - `vol_target`：组合级波动率目标——组合实际波动率超目标时按比例
    收缩新开仓规模/总敞口（Carver 式 vol targeting，二期首批模块）；
  - `drawdown_throttle`：回撤节流——组合回撤越线（如 −10%）时降风险
    预算或暂停新开仓，修复后恢复（二期首批模块）；
- 每个 gate 拒绝时记原因——"被风控拦下的候选"与未成交订单一样是研究素材，
  落 run 日志。

#### 5.2.6 `position_risk` 持仓风控

```
protocol PositionRiskModule:
    def init_stop(self, ctx, fill) -> StopState
    def evaluate(self, ctx, position, bar) -> ExitOrderIntent | None
    def estimate_stop(self, ctx, symbol) -> float   # sizing 的预估输入
```

- 买入成交后初始化止损状态（`init_stop`，入 Position 快照）；
- 每日评估：返回卖出意图（引擎负责盘中触及/跳空/跌停顺延的成交语义，
  见 §4.2）；
- 内置实现：`hard_stop`、`chandelier`、`ratchet`、`time_stop`（持有 N 日
  强制离场，实验素材）——全部委托 `engine/stops.py`（收编后的唯一实现，
  实际买入价基准、ATR 含当根）；
- `estimate_stop` 在买入前给 sizing 用（拟止损价），口径与 init_stop 一致
  （差异只在 ATR 基准时刻：预估用 as_of 数据，实际以成交日为准）；
- 两处协议补强（止损表达力调研结论，详见 §4.3.1）：`StopState` 带不透明
  `module_state: dict`（PSAR 加速因子、保本激活位等模块自定义状态随持仓
  快照落库）；`ExitOrderIntent` 带 `fill_mode: intraday_stop | tail` 区分
  盘中触及型与收盘确认型离场（均线止损等"收盘跌破才算"的语义用 tail）。

#### 5.2.7 `execution` 执行

```
protocol ExecutionModule:
    def fill_policy(self) -> FillPolicy        # 尾盘模型参数（滑点等）
    def rotation_policy(self, ctx, candidates, holdings) -> list[ExitOrderIntent]
```

- `fill_policy`：MVP 只有一种——T 日尾盘成交（基准价=收盘，滑点参数化）；
  它的存在是为了让"成交时点"成为可实验的插槽，而不是写死在引擎里；
- `rotation_policy`：槽位满时的轮换决策。MVP 默认 `hold_first`（持有优先，
  不主动踢仓）；缓冲轮换（新信号分 > 最差持仓 × (1+buffer)）为二期实验素材；
- 调仓默认**事件驱动**（止损/退出 → 空槽 → 新信号填补）；日历驱动
  （月度检查、定期再平衡）通过 execution 的"行动门控"频率参数表达，
  不是第二种范式（见 §5.11 缺口①）。

### 5.3 策略配置格式与版本化

策略 = 一份 YAML 配置（不是代码）：

```yaml
name: base-v1
description: 当前实盘打法 1:1 复刻（基准策略 v1）
universe:   {module: category_filter@1, params: {levels: [...], liquidity: {...}}}

  - {module: slot_limit@1,   params: {max_positions: 10}}
```

规则：

- 每个引用必须是 `registry` 中的已注册模块（name@version），参数过该模块的

- 入库即冻结：`strategy_versions` 存 (strategy_id, version, config_yaml,
  config_hash, created_by, created_at, experiment_id?, parent_version?)；

  在配置层自然成立（diff 可机器计算）；
- 血缘在回测运行时补全：data_version、engine_version、git_hash 记入
  engine_runs（见 §4.1）。

### 5.4 组合回测器（backtester.py）

#### 5.4.1 日循环（尾盘口径）

```
for t in trading_days(start, end):
    ctx = DayContext(date=t, as_of=close(t), ...)

    # 1. 持仓风控：逐持仓 evaluate → 止损/退出意图（盘中语义由引擎执行）
    for pos in account.positions:
        intent = position_risk.evaluate(ctx, pos, bar(t, pos.symbol))
        if intent: engine.submit(intent)          # 盘中触及按止损价/跳空按开盘

    # 2. 信号扫描（universe 内，含持仓标的的 exit 事件）
    members = universe.members(ctx)
    events  = signal.scan(ctx, members)
    exits   = [e for e in events if e.kind=="exit" and held(e.symbol)]
    entries = [e for e in events if e.kind=="entry" and not held(e.symbol)]
    for e in exits: engine.submit(sell_all(e.symbol))   # 尾盘卖出

    # 3. 候选竞争：排序 → 定量 → 组合风控
    ranked  = rank.rank(ctx, entries)
    intents = [i for c in ranked
               if (i := sizing.size(ctx, c, position_risk.estimate_stop(ctx, c.symbol)))]
    admitted = intents
    for gate in portfolio_risk: admitted = gate.admit(ctx, admitted, pending_exits)

    # 4. 尾盘成交（引擎执行卡控/费用/T+1），未成交落 engine_unfilled
    for i in admitted: engine.submit(i)

    # 5. 日结：NAV、heat、exposure 落 engine_daily_nav
```

#### 5.4.2 关键语义（明确写死，避免实现期自由发挥）

- **同一标的同日先卖后买**：exit 成交释放的现金/槽位当日可用于新买入
  （尾盘模型下视为同一时点，允许）；
- **同日同标的边卖边买**：不允许（exit 与 entry 同标的同日，entry 忽略）；
- **买入失败不递补**：admitted 清单因涨跌停/现金未成交的，当日不再顺次
  递补下一名（诚实建模"那一刻你就想买它"）；错过的进 unfilled 供研究；
- **止损与信号同日冲突**：止损优先（先风控后信号，见日循环顺序）；
- **卖出全部整仓**，无部分卖出（MVP）；
- **不加仓**（MVP 不做金字塔；每个持仓一笔买入）；
- **空仓资金零收益**，无融资；
- **窗口与样本**：默认 2020-01-01 起（数据深度现状），ends 于最近交易日；
  sample/holdout 窗口由 L4 传入（见 §6.6.4），backtester 本身不感知。

**以上规则的血缘说明（诚实交代，非业界标准流程）**：日循环的骨架——
"卖优先于买（先出场后入场）、风控先于信号、日频事件驱动"——是业界日频
回测器的通行惯例（backtrader 的 next() 习惯序、LEAN 的框架模块序、qlib
的 TopkDropout 均同构）；但**不存在"业界标准 5 步"**，具体步骤划分与上述
8 条规则是为本系统（尾盘口径、A 股 T+1、七插槽）拍的设计决策。其中
"买入失败不递补"业界两派都有（qlib TopkDropout 的 only_tradable 模式实际
是递补派），我选了诚实建模派——这条本身就是未来一个合法实验
（execution 槽参数），不是真理。

#### 5.4.3 输出

除 engine_* 各表外，`reports.py` 汇总：

- 组合级：NAV 曲线、年化/最大回撤/Sharpe/Sortino/Calmar（复用
  `rule_backtest/metrics.compute_summary`，输入组合 NAV 即可）；
- **业界通用指标的补充清单**（对照 pyfolio/QuantStats/PortfolioAnalytics
  惯例补齐，NAV 序列可得的全是廉价计算）：
  - **相对基准统计**：alpha、beta、Information Ratio、tracking error、
    超额收益、上/下行捕获率——benchmark 对比不能只是画线；
  - **稳定性**：滚动 Sharpe（6m/12m 窗口）、回撤持续期/修复时间
    （水下曲线的时长维度，比"多深"更折磨人）；
  - **收益分布**：偏度、峰度、尾部比、VaR/CVaR（日频）；
  - **成本拖累**：费用合计 ÷ 毛收益——A 股成本环境下每条规则的
    及格线（调研文档：年化换手每 +100%，期望收益先扣 0.2~0.3%）；
- 组合特有：heat 曲线、槽位利用率（持仓数/上限）、换手率、exposure 曲线、
  行业集中度时序；
- 事件级：round trips（复用现有 RoundTrip 诊断：R 倍数/MAE/MFE）、
  unfilled 统计（按原因）、风控拦截统计（按 gate）；
- 对照：**benchmark 多选**——报告展示层可叠加任意多个 benchmark 策略
  曲线（buy&hold + 60/40 + SMA200 择时 + …，见 §5.5）。注意两个概念别混：
  **L4 实验的"对照"是算 deltas 的基准策略，单一**（保证实验可比性）；
  **报告的 benchmark 展示是多选**（看策略在怀疑阶梯上的位置）。

### 5.5 策略库（library.py）

- **入库规则**：必须带 (config_hash 唯一、血缘可填、产出实验 id 或 benchmark
  标记)；版本不可变，删除只做软标记且不影响已被引用的运行；
- **benchmark 策略首批**（配置即策略，直接入库）——按"怀疑阶梯"组织，
  每个回答一个具体问题：
  1. `buy_hold_csi300`：买入并持有沪深 300ETF——**"你跑赢躺平了吗"**；
  2. `bond_stock_60_40`：60/40 股债（沪深300ETF + 国债ETF，年度再平衡）——
     **"你跑赢傻瓜分散了吗"**（业界最经典的配置基准）；
  3. `sma200_timing`：Faber SMA200 择时（单宽基，线上持有线下空仓）——
     **"你跑赢最简择时了吗"**（把"择时有用"和"你的择时有多好"分开）；
  4. `simple_momentum_rotation`：简单动量轮动（20 日动量最强的 1 只宽基
     ETF，月度检查）——**"你跑赢傻瓜动量了吗"**；
  5. `random_entry`：随机入场 + 与基准相同的止损——**"你的信号比猴子强吗"**；
  6. `random_pick`：候选产生后随机选择——**"你的 rank 槽值多少钱"**；
  7. `equal_weight_universe`：universe 等权——**"你的事件驱动机制比
     全摊强吗"**；
  8. `blank-base@1`：空白基准（七插槽全 none，不产生交易）——不是
     benchmark，是**新策略实验的 diff 起点**（见 §6.1.4）。
- benchmark 与正式策略同构（同样是七插槽配置）——"无脑默认"在插槽级与
  策略级都是一等公民（架构稿 §2.5 纪律 1）。

### 5.6 对外服务面：L4 调用 L3 的唯一入口

原则：**L4 只提交声明式 spec，从不自己实现或组装策略对象**。策略的组装、
校验、执行全部在 L3 内完成（分层隔离的实体化）。

运行级接口：

- `resolve_experiment_config(base_version_id, diff) -> resolved_config`：
  将"基准 + 插槽 diff"解析为完整策略配置——模块存在性、参数域、插槽
  完整性全部在此校验；返回带 config_hash 的解析结果；
- `run_backtest(resolved_config, window_kind, window) -> run_id`（异步入队）；
- `get_run_status(run_id)` / `get_run_report(run_id)`；

只读目录：`list_modules(slot?)`、`get_strategy_version(id)`（含血缘）。

**可复现性规则**：解析后的完整配置 YAML 随 run 落库
（engine_runs.resolved_config_yaml），不是只存 hash——实验引用的策略
永远可复现，哪怕它从未入策略库。策略库只收晋升的策略（带实验血缘）；
实验期的策略是"解析即弃"的临时配置，但完整内容留在 run 记录里。

### 5.7 实盘运行器（live.py，薄版，决策 3）

**与组合回测器的关系：同一个策略对象、同一条决策代码路径**（架构稿
"回测实盘同路径"的落实）。差异只有四点：

| 维度 | 组合回测器 | 实盘运行器 |
|---|---|---|
| 触发 | 批处理（实验/手动发起） | 定时任务，交易日 14:00 |
| 数据 | 历史面板（as_of=历史某日） | live 模式（as_of=now，含盘中合成 bar） |
| 输出 | 引擎真实撮合成交 + 指标落库 | **只出清单，不撮合**——目标持仓 + 应买应卖 |
| 账户状态 | 模拟账户（引擎维护） | 真实记账（manual_trades + 对账模块重建） |

注意：实盘运行器**不是**执行系统（不碰券商接口，决策 3）——它出清单，
人执行，系统对账。每日流程：

1. 以 `live` 模式经 gateway 取数（含截至 14:00 的盘中合成 bar，as_of=now）；
2. 加载已部署策略版本 → 跑单日决策（与日循环步骤 1–4 相同，但只输出
   订单清单不真实"成交"）；
3. 输出**目标持仓 + 应买应卖清单**（含建议数量、拟止损价、风控拦截说明）；
4. 用户在券商 App 手工执行后录入 manual_trades；对账模块比对：
   应买未买/应卖未卖/成交价 vs 收盘基准价的偏差 → 执行差统计，
   **用于标定引擎 slippage_tail 参数**（架构稿 §3.2：对账的第二个价值）；
5. 并行期（一个月）：只出清单不建议动作，与实盘对照验证后再转正式。

### 5.8 与旧分支的边界

- 复用：`core/indicators`（MACD/ATR 等单一实现）、`metrics.compute_summary`、
  RoundTrip 诊断口径、费用常量（迁入 engine/fees 后旧分支自留副本）；
- 不复用：rule_backtest 的条件引擎（扁平 AND/OR 配置）不迁入——组合层的
  signal 是协议化模块，配置表达力需求不同（架构稿：旧分支配置思路保留在
  旧分支）；
- 迁移顺序：先迁 risk_budget 数学（sizing 删包前置），止损收编随阶段 1，
  实盘试算器随阶段 4 再定。

### 5.9 MVP 边界（明确不做）

不做：加仓/金字塔、部分卖出、**主动轮换**、做空、时点动态池（等数据线）。
说明两条易被误读的：

- **"不轮换"≠"不调仓"**：事件驱动调仓（止损/退出 → 空槽 → 新信号填补）
  在 MVP 内，组合天天在调。不做的是**主动轮换**（把未止损的弱势持仓
  踢掉换新信号）——依据：持有优先是趋势跟踪的主流立场（无缓冲的轮换
  会被成本来回打脸），且 hold_first 是最简正确基线；缓冲轮换是
  execution 槽的一个模块，基线验证后第一批实验就该测它，不是被排除；
- **周/月 K 信号：从"不做"修正为"非首批"。** 数据层完全能供（自然周/月
  与滚动口径 L1.5 都可提供），信号协议也无障碍——它只是"注册一个新
  signal 模块"的事。MVP 首批模块只做日频的理由是控制口径爆炸：
  周/月信号绕不开 provisional bar 语义（未收盘的周/月 bar 算不算数），
  这套口径本项目刚经历过 v1→v4 的混乱，教训还热着，先在日频把闭环
  跑稳，周/月模块随时可加（且日频信号 + rolling 趋势值已间接覆盖
  周/月信息）。

每一项边界都是后续合法实验的素材，不是遗漏。

### 5.11 常规策略的插槽表达力验证

自顶向下设计的插槽必须拿常规策略逐个试装。验证结果：**事件驱动的趋势/
动量家族全覆盖；发现一处真缺口（日历门控）已给出插槽内解法；两处边界
与既有 MVP 边界一致**。

| 策略 | 七插槽装配 | 结论 |
|---|---|---|
| MACD 金叉趋势（base v1） | 见 §5.3 示例 | ✅ 基准本身 |
| 海龟/唐奇安突破 | signal=`channel_breakout@1`(20 日新高入/10 日新低出)、sizing=`equal_risk`、position_risk=`chandelier`、rank=`by_freshness`、gates=slot+heat | ✅ 全内置模块 |
| Faber SMA200 TAA（宽基线上持有、线下空仓） | universe=单标的、signal=`ma_cross@1`(n=200)、sizing=`all_in`、position_risk=`none` | ✅ |
| 52 周新高策略 | signal=`high_52w@1`，其余同 v1 | ✅ |
| 双动量 ETF 轮动（Antonacci：月度检查、绝对动量>0 才持有、相对最强） | signal=`abs_momentum@1`、rank=`by_momentum`、execution 需**月度检查门控** | ⚠️ 见缺口① |
| 动量轮动+缓冲带宽（Clenow：slope×R² 打分、跌出前 2N 才卖） | rank=`by_slope_r2`、execution=`buffered_rotation` | ⚠️ 模块属二期，但 `rotation_policy` 协议已预留，插槽不破 |
| 核心-卫星杠铃（红利+科技固定权重、偏离超带宽再平衡） | sizing=`target_weight@1`（OrderIntent 的 `target_weight` intent 协议设计已预留）、execution=`rebalance_band@1` | ⚠️ 注册两个新模块即可，插槽不破 |
| 网格 / 定投 / 金字塔加仓 | 需要加仓 + 部分卖出语义 | ❌ 与 §5.9 MVP 边界一致（二期加仓语义） |
| 多空 / 市场中性 | 需要做空 | ❌ MVP 不做空 |

**缺口①（真发现）：日历驱动策略。** 双动量的"每月检查一次"、配置型的
"定期再平衡"，与 §5.2.7"调仓是事件驱动、无日历调仓"冲突。解法不新增插槽：
**execution 槽补"行动门控"语义**——信号照常每日计算，但模块按频率参数
（每 N 交易日 / 每月第 1 个交易日）决定哪些日子允许行动（新开仓/轮换/
再平衡）。语义修正：MVP 的默认执行是"事件驱动、每日可行动"；日历驱动是
execution 的一个频率参数化变体，不是范式外的第二种策略。`market_gate`
等风控评估不受门控影响（每日照常）。

**结论**：七插槽对"日频、多头、趋势/动量 + 配置型"常规策略的表达力验证
通过；两个 ⚠️ 都是"注册新模块"级别，不破插槽协议；两个 ❌ 是既有边界。

### 5.12 业界对标审计

按"已对齐 / 有意偏离 / 业界通用但缺失"三档审计全部设计。

#### 5.12.1 已对齐（业界通行做法，与本设计一致）

- 日循环骨架：卖优先于买、风控先于信号（backtrader/LEAN/qlib 同构）；
- 订单/成交/持仓/账户模型（vnpy/LEAN 对照，决策见 §4.1）；
- 费用与 A 股规则（佣金/印花税/最低 5 元/整手/T+1/涨跌停/停牌）；
- 报告指标（§5.4.3 已按 pyfolio/QuantStats/PortfolioAnalytics 补齐）；
- benchmark 怀疑阶梯（买入持有/60-40/SMA200 择时/简单动量/随机系）；
- 策略版本化 + 血缘（策略入库不可变，业界实验追踪惯例）。

#### 5.12.2 有意偏离（已定论，仅备查）

- **成交口径 T 日尾盘/收盘**：业界回测器默认多为次根 bar 开盘成交
  （zipline/backtrader/qlib）。本项目按决策 1 定为 T 收盘 + 尾盘滑点 +
  实盘对账标定，残余前视已声明并持续标定；
- **买入失败不递补**：qlib only_tradable 模式为递补派，本项目选诚实
  建模派，且该规则本身是 execution 槽的合法实验素材。

#### 5.12.3 业界通用但本设计缺失（已定结论）

| # | 业界做法 | 说明 | 结论（2026-09-22 用户确认） |
|---|---|---|---|
| A | 现金管理收益 | 闲置资金按货基/逆回购利率计息（机构 NAV 惯例） | **接纳**：空仓时段多是本系统常态，逆回购/货基实盘可执行；实现为账户参数 cash_yield（见 §4.4） |

### 5.13 复杂组合策略怎么装：业界手段 → 插槽映射 + 完整示例

先正面回答"业界从几百只里怎么筛出要买的、怎么控制组合整体仓位、怎么
调仓"这三个问题，以及每个动作住在哪个槽：

| 业界动作 | 具体手段 | 住哪个槽 |
|---|---|---|
| 资格过滤（池子里谁配被考虑） | 流动性门槛、ST/停牌/黑名单、上市时长、板块限定 | `universe` |
| 触发（今天谁出现了机会） | 金叉/突破/动量转正/趋势穿越（事件） | `signal` |
| 打分排序（机会之间谁先谁后） | 多因子综合分、动量分、趋势质量、信号新鲜度 | `rank` |
| 单笔定量（这只买多少） | 等风险、波动率倒数、固定权重/金额 | `sizing` |
| 总量控制（组合最多承担多少） | 槽位数、组合热上限、行业中性/集中度 | `portfolio_risk` |
| 总敞口调节（现在该不该加仓） | 波动率目标缩放、回撤节流、大盘/breadth 闸门 | `portfolio_risk` |
| 单票离场 | 止损/止盈/时间止损（§4.3.1 全族） | `position_risk` |
| 调仓 | 事件驱动（默认）、日历门控（月度检查）、带宽再平衡（偏离>X% 才调）、top-k 缓冲轮换 | `execution` |

一句话回答"七插槽够不够承接复杂度"：**策略的复杂度住在模块实现里，
插槽只管复杂度住在哪**。业界组合策略没有第七种动作——筛选、触发、排序、
定量、总量、离场、调仓，全部各有其槽。

**完整示例**：一个"全市场趋势动量组合"（把多个业界机制叠满，演示复杂度
承接能力）：

```yaml
name: trend-momentum-full
universe:   {module: liquidity_filter@1, params: {min_amount20: 1e8,
              exclude_st: true, asset_type: all}}        # 资格过滤
signal:     {module: channel_breakout@1, params: {entry_n: 20,
              exit_n: 10}}                               # 唐奇安突破触发
rank:       {module: by_slope_r2@1, params: {window: 90}}# Clenow 斜率×R² 打分
sizing:     {module: equal_risk@1, params: {risk_budget_pct: 0.0075}}
portfolio_risk:                                          # 五重组合风控叠加
  - {module: slot_limit@1,        params: {max_positions: 12}}
  - {module: heat_cap@1,          params: {max_heat_pct: 0.06}}
  - {module: concentration_cap@1, params: {per_l2: 2}}
  - {module: market_gate@1,       params: {breadth_mid: [0.3, 0.7],
      action: halve_risk}}                               # breadth 中段风险减半
  - {module: drawdown_throttle@1, params: {dd_line: -0.10,
      action: halt_new}}                                 # 回撤 10% 停新开仓
position_risk: {module: chandelier@1, params: {atr_mul: 2.5}}
execution:  {module: tail_session@1, params: {slippage_base: 0.002,
              slippage_tail: 0.001,
              action_gate: {freq: daily},                # 每日可行动（事件驱动）
              rotation: hold_first}}                     # 持有优先不主动踢仓
```

**它一个交易日怎么跑**（2024-03-15 的实况推演）：

```
1. 持仓风控：12 只持仓逐一评估吊灯 → 512880 触发（止损 5.21，现价 5.19）
   → 引擎盘中按 5.19 成交卖出（fill 落库，释放现金 2.7 万 + 1 个槽位）；
2. 信号扫描：流动性池 743 只 → 20 日突破事件 9 个（含 1 只持仓，忽略其
   entry）；另有 1 只持仓出 exit 信号（10 日新低）→ 尾盘卖出；
3. 排序定量：8 个候选按 slope×R² 降序 → equal_risk 逐个定量
   （如 600519：权益 30 万×0.75% ÷ (1680−1598)×100 ≈ 2700 股）；
4. 组合风控五连闸：slot 11/12 剩 1 位 → 只放第 1 名；
   heat 当前 4.9% + 新增 0.4% = 5.3% < 6% 过；集中度：第 1 名是白酒，
   已有 2 只食品饮料 → **concentration_cap 拦截**，原因落 run 日志；
   顺次看第 2 名（半导体，过）……最终放行 1 只；
   breadth = 0.55 处中段 → 风险预算减半：定量 2700→1300 股；
5. 尾盘成交：基准价=收盘 ×(1+0.003)，整手/现金/涨跌停卡控；同日另一只
   放行候选收盘涨停 → engine_unfilled(reason=limit_up)；
6. 日结：equity/heat/exposure 落 engine_daily_nav。
```

## 6. L4 投研层（research 包）

> 依赖：只调 L3（portfolio）与 L1.5（gateway）；不直连 L1/L2。

### 6.1 实验的重新定义（本层的核心）

实验 = **固定骨架 + 一个已注册的评估模块 + spec + 假设 + verdict**。

#### 6.1.1 固定骨架（认识论，所有实验强制、无例外）

1. **假设先行**：hypothesis 非空，先写故事后看数；
2. **对照显式声明**：每个实验必须声明它的对照是什么——基准策略 / 无条件
   收益分布 / 随机 / 另一个信号。对照的形式随评估方法不同，但不能没有；
3. **单变量**：一次只动一个"东西"。"东西"的定义随评估方法而定：
   回测实验里 = 一个策略插槽；事件研究里 = 一个事件定义；分桶里 = 一个特征；
4. **结论 = 相对对照的差值**，不记绝对指标；
5. **台账铁律**：verdict 平台生成、append-only、全员只读、血缘完整、
   尝试计数 + 显著性折扣。

#### 6.1.2 可插拔评估方法（取证手段）

`evaluation` 是实验对象的必填字段，取**评估模块注册表**中已注册模块
（name@version，治理同 §6.2.2）。首批四个：

| 评估模块 | 回答的问题形态 | 取证方式 | 对照 | 覆盖的历史研究形态 |
|---|---|---|---|---|
| `portfolio_backtest` | 机制类（止损/仓位/风控/排序/执行） | 基准策略 + 插槽 diff → 调 L3 组合回测 | 基准策略，Δ指标 | 组合层研究（机制半） |
| `event_study` | 这个信号/事件有没有料；历史统计规律挖掘 | 事件扫描（可带 regime 条件过滤）→ 前瞻 N 日收益/胜率/路径统计（恢复时间/MAE/MFE）/迁移矩阵，向量化 | 无条件收益分布（全标的全日） | 相位迁移 v1–v4；卖方"历史 N 次 X"类研究 |
| `bucket_analysis` | 这个截面特征有没有排序力 | 信号日截面按特征分 M 组，看各组前瞻收益单调性 | 随机打乱 / 反序 | 组合层研究（分桶半）、调研 §2.3 |
| `distribution` | 这个参数该怎么标定 | 全市场池化分布统计 | 弱对照（预设判断准则） | 趋势值分布、±9 标定 |

规则：

- **新增研究形态 = 新增注册评估模块（人审），不是新增实验类别**——骨架、
  台账、纪律一动不动；
- **spec 不过度设计：平台 schema 只卡骨架字段**（evaluation_module、
  hypothesis、对照声明、自由变量标识、数据窗口——只有它们是机器检查
  "单变量"和"有对照"的依据）；**spec 的具体内容由评估模块自定义**——
  模块 = 代码 + 参数空间，随模块版本演化（加参数 = minor version）。
  新研究角度的处置顺序：先扩模块参数 → 不够再注册新模块（人审）→
  平台 schema 永远不改。各模块的 spec 示例只是该模块当前参数空间的
  快照，不是规格；
- 所有评估模块的数据只经 L1.5 gateway（as-of 强制）；`portfolio_backtest`
  委托 L3，其余三个在 research 包内向量化自算（"只要数据不要引擎"，
  正是 L1.5 独立成层的用例）；
- `distribution` 的对照最弱，其 verdict 被限定为"参数标定建议"，**不能**
  作为策略改动的直接依据（要改动策略，仍需 backtest 实验）。

#### 6.1.3 信号模块的双重身份（研究路径闭环）

L3 的 signal 插槽模块（如 `macd_cross`、`ma_cross`）同时是 `event_study` /
`bucket_analysis` 合法的事件定义来源——同一个注册模块、同一份代码。于是
标准研究路径：

```
event_study（这个信号有没有料：金叉后 5/10/20 日 vs 无条件分布）
   │ 有料
   ▼
portfolio_backtest（做成完整策略赚不赚钱：基准 v1 的 signal 槽换成它）
   │ deltas 过纪律流水线
   ▼
策略库入库（带两级实验血缘）
```

两级实验在同一信号模块上血缘相连——"这个策略信号当初的 event_study 证据
是什么"可一键回查。

#### 6.1.4 L4 → L3 的调用契约

"L4 按 L3 的接口契约自己实现策略"还是"L3 开放接口给 L4"？答案是后者：
**L4 只提交声明式 spec，策略的组装、校验、执行全在 L3**（分层隔离的
实体化）。AI/人开启一次实验的完整链路：

```
research.propose_experiment(evaluation_module, spec, hypothesis)
  → 骨架校验（§6.6.1：假设/对照/单变量/引用/计数）
  → backtest 类：调 L3 resolve_experiment_config 解析并校验配置
  → 入有界并发池
  → 执行（portfolio_backtest 委托 L3 run_backtest；
          event/bucket/distribution 在 L4 内经 gateway 向量化自算）
  → verdict 流水线（§6.5 证据 + §6.6 纪律）
  → verdicted（必须落定 final_verdict + reasoning，见 §6.4）
```

L4 的 api.py 是通道无关的服务面（MCP/CLI/Web 皆为薄通道）；L3 对 L4
暴露的服务面见 §5.6。

**新策略从哪进（"我有一个全新策略想法"的情形）**：

先区分两类实验（一等区分，不是例外）：

| | 创建型实验 | 改进型实验 |
|---|---|---|
| 对象 | 整个策略 | 一个改动 |
| 基准 | `blank-base@1`（空白基准：七插槽全 none，不产生交易） | 策略线上的某个已入库版本 |
| diff | **七槽全填（合法，不降档）** | 强制单槽 |
| 对照 | benchmark 怀疑阶梯（买入持有/60-40/SMA200…） | 基准策略（算 deltas） |
| 回答的问题 | "这个策略整体值不值得存在" | "这个改动有没有用" |

原理：单变量纪律的目的是**归因**（"回测好了是哪个改动起的作用"）；
创建时还没有任何"改动"存在，归因问题不存在，所以全槽填充不受单变量
约束。平台按 `base == blank-base@1` 自动识别创建型实验：免 compound
降档、对照自动切到 benchmark 阶梯。

创建流程就是一次填表——七个槽各选模块和参数、一次提交、一次回测，
无额外步骤：

示例：AI 的想法"52 周新高突破买入 + 等风险仓位 + 吊灯止损"落成调用：

```python
propose_experiment(
  evaluation_module="portfolio_backtest@1",
  hypothesis="52周新高突破有入场 edge，策略化后跑赢买入持有与最简动量",
  spec={"base": "blank-base@1",     # 平台据此自动识别为创建型实验
        "diff": [                    # 七槽全填，无 compound 降档
          {"slot":"universe",      "to":"liquidity_filter@1","params":{"min_amount":1e8}},
          {"slot":"signal",        "to":"high_52w@1"},
          {"slot":"rank",          "to":"by_freshness@1"},
          {"slot":"sizing",        "to":"equal_risk@1","params":{"risk_budget_pct":0.0075}},
          {"slot":"portfolio_risk","to":["slot_limit@1(10)","heat_cap@1(0.06)"]},
          {"slot":"position_risk", "to":"chandelier@1","params":{"atr_mul":2.5}},
          {"slot":"execution",     "to":"tail_session@1"}]})
```

→ L3 `resolve_experiment_config` 叠加解析出完整策略配置（校验模块存在、
参数合法）→ `run_backtest` 执行 → verdict 给出 vs 空白基准 + benchmarks
的结论 → 想固化则晋升入策略库，成为新策略线 v1（后续迭代回到标准
单槽 diff，subject_key = 新策略线）。

**前提**：diff 引用的都是已注册模块；引用不存在的模块被 resolve 拒绝，
转 `propose_module`（§6.2.2 自动测试门）——AI 永远不能用未过测试门的
代码。

### 6.2 模块构成

```
research/
  experiments.py    # 实验对象模型、创建校验（骨架五条 + 各模块 spec schema）
  evaluations/      # 评估模块（注册表与实现）
    backtest.py     # portfolio_backtest（委托 L3）
    event.py        # event_study（向量化，gateway 面板）
    bucket.py       # bucket_analysis（向量化）
    distribution.py # distribution（向量化）
  lifecycle.py      # 生命周期状态机
  verdict.py        # verdict 统一信封 + 各模块 verdict 生成器
  holdout.py        # sample/holdout 窗口管理与放行（对全部评估模块生效）
  ledger.py         # 台账读写（append-only 强制）、重复检测
  sessions.py       # 会话归属
  api.py            # 对人/AI 暴露的服务面（通道无关）
  worker.py         # 有界并发池执行器
```

#### 6.2.2 模块治理：自动测试门 + 人抽检（无人审必经门）

模块是代码，不是数据——但治理手段要对症，前视问题不该由人审扛：

- **数据越界类前视是 L1.5 的职责**（as-of 强制，模块物理上取不到未来
  数据），不靠审；
- **逻辑类前视由平台自动探针抓**：模块注册时自动跑"前缀稳定性测试"——
  同模块分别在截断到 t 与 t+30 的数据上运行，≤t 的输出必须位级一致，
  不一致 = 有前视，拒绝注册（freqtrade lookahead-analysis 同款思路）；
- **契约与确定性自动测试**：返回类型 / 无副作用 / 同输入同输出；
- **人 = 抽检与下架权，不是必经门**：公式正确性（ATR 周期写错这类
  "自洽的错误"）自动测试抓不住，靠 golden 值测试（标准模块）+ 人抽检
  + 台账可复审（§6.5.0 报告完整性）兜住。

DSL 表达式类模块（算子白名单、构造上无前视）免测试直接用——安全由
DSL 引擎构造保证。

流程：AI `propose_module` → draft 落库（保存自由、台账可见）→ 自动
测试门 → 通过即 reviewed、可被实验引用；不通过附原因打回。人随时可
抽检、可下架；下架只禁止新引用，不影响已完成实验的记录（run 里存有
resolved 配置与模块版本，可复现）。

（L3 的策略插槽模块、L4 的评估模块同制。）

### 6.3 对象模型与存储表

### 6.4 生命周期状态机与研究课题

```
proposed ──骨架校验+spec校验──► rejected_intake（记原因，也留痕）
    │ 通过
    ▼
queued ──并发池调度──► running ──取证完成──► evaluating
    （verdict 流水线：证据计算 + 对照差值 + 警告 + 判定建议）
evaluating ──► verdicted（final_verdict 落定）──► archived
    └─ 运行失败 ──► failed（工程失败，入表；不等于假设被证伪 rejected）
```

规则（状态机由平台强制，不是靠自觉）：

- 状态转移只能经定义动作触发（提交校验 / 池调度 / 取证完成回调 /
  confirm_verdict），非法转移直接拒绝——实验不能跳步（比如从 proposed
  直接到 verdicted）；
- **实验必须到达终态**：`verdicted` / `failed` / `rejected_intake` 三态之一。
  到达 verdicted 的前置条件是 final_verdict + reasoning 均已落定——
  即每个实验必须有明确结论，不允许"跑完放着不管"；
- **烂尾巡检**：evaluating 超过 N 天（如 7 天）未确认的实验进入烂尾清单，
  对 owner 提醒并在台账可见；平台不自动关闭（结论不能伪造），但烂尾
  本身是公开可见的失信记录；
- 任何终态留台账（成败同等入表）；`final_verdict` 允许降级、不允许升过
  平台建议；reasoning 必填。

#### 6.4.1 研究课题（topic）：每个实验的必选归属

层级关系固定为两级：**课题（研究问题）→ 实验（对该问题的一次检验）**。
实验创建时必须归属一个课题（topic_id 必填；没有合适的就顺手新建——
课题创建只需 title + question，无额外成本）。这同时加强了骨架第 1 条：
研究从问题出发，不允许"无课题的漫游式实验"。

- **课题不是实验**：平台不为其计算 verdict。课题结论 = 创建者综合子
  实验 verdict 的文本，平台只校验：引用的实验必须都已到达 verdicted
  终态（不许引用半成品）；
- 课题强制终态：open → concluded（必须写 conclusion），同样进烂尾
  巡检；
- **课题与实验都上看板**：台账全员只读开放，可浏览"历史上做过哪些
  课题、结论是什么、各挂哪些实验"——新会话的 AI 先读课题板再提假设，
  是重复检测之外第二道防重复研究的机制；
- 与 parent_experiment_id 的分工：parent 链管"同一基准上的串行修正"
  （一条线的迭代），topic 管"一个问题下的多分支协同"（可跨插槽、
  跨评估模块，如"止损研究"同时含 backtest 消融和 event_study 统计）；
- 复杂度控制：课题保持轻量（问题 + 状态 + 结论 + 引用校验），不许
  长出自己的指标体系；
- **每个课题一个文件夹**（`research/topics/<topic_id>_<slug>/`）：
  `TOPIC.md`（问题/结论/实验清单）、`experiments/<exp_id>/REPORT.md`
  + `report.json`（完整报告，见 §6.5.0）、`manifest.json`（复现清单：
  spec 全文、模块版本、data_version、engine/git 版本、窗口）、
  以及课题内的 ad-hoc 分析脚本。实验是声明式的，所以"复现代码"=
  spec 本身（`research rerun <experiment_id>` 即可重跑）。
  **看板（DB）是查询面，文件夹是阅读/审计/复现面**——两者由平台从
  同一份记录生成，永不手工维护、可再生成；别的 AI 不只读到结论，
  还能找到报告原文、拿到 spec 与版本清单直接复现。manifest 里的
  data_version 同时承担诚实义务：若重跑时数据已重述（qfq 改写），
  版本差异会被显式标出，而不是悄悄不一致。

### 6.5 评估模块的 verdict 规格

统一信封（所有模块一致）：`baseline / evidence / warnings / suggested_verdict
/ report`。

#### 6.5.0 report：完整实验报告（不是摘要）

每个实验/课题必须产出**完整报告**（research_verdicts.report_json，机器
可读；课题报告同理挂在 topic 上）：假设与 spec 全文、模块版本、数据
窗口与 data_version、**完整结果明细**——backtest 含全指标表 + regime
逐段数值 + 高原各点 + 交易/未成交/风控拦截统计；event_study 含逐
horizon、逐组合明细与迁移矩阵；bucket 含逐组数值与单调性检验量。
一个都不许摘要化。

理由：**报告完整性是"AI 能审计前人实验"的前提**。后来读台账的 AI
看到的不是"信号太密、震荡市打脸"这种浮于表面的结论，而是"信号密度
= 12.4 次/年/标的、SMA200 下段 ΔSharpe = −0.31"这种可审计的细节——
由此它才能发现原实验的设计漏洞（样本期太短、口径缺陷、某 regime 被
忽略），并提出修正实验（parent 链接回原实验）。台账因此从"结论库"
升级为"可复审的研究档案"。报告同时物化到课题文件夹
（`research/topics/.../REPORT.md` + `report.json` + manifest，见 §6.4.1）。

各模块证据与判定：

#### 6.5.1 `portfolio_backtest`

- 证据：实验 vs 基准同窗的 Δ年化/Δ回撤/ΔSharpe/ΔSortino/Δ换手/Δ费用，
  regime 拆分（基准 SMA200 上/下 + breadth 三档）；
- 高原补跑：diff 中数值参数邻域补跑（邻域表按参数类型：止损倍数 ±20%、
  持仓数 ±2 只、天数 ±20% 取整）→ plateau|peak。判定除"三点同向"外，
  并入 Alvarez 式标准差检查：**选定参数的结果偏离邻域均值 1σ 以上 →
  疑似过拟合**（孤峰不一定是两侧塌，也可能是整体噪声里的幸运点）；
- 判定建议：主指标改善 + plateau + regime 无塌陷 + 换手增幅成本可解释
  **且 DSR > 0**（§6.6.5）→ confirmed；显著恶化 → rejected；其余
  inconclusive；
- 样本外选项（2026-09-22 审计 F/G 项接纳，二期）：spec.window_mode =
  `static_holdout`（默认）| `walk_forward`（滚动样本外，多次 OOS 的制度
  化）；verdict 可选叠加蒙特卡洛置信带（交易序列 bootstrap / 参数扰动）。

#### 6.5.2 `event_study`

spec 示例（`event_study@1` 当前参数空间的快照，**非平台 schema**；参数随
模块版本演化，覆盖"6 轮牛市 99 次考验 MA20"类研究）：

```
spec: {
  event: ma_touch@1(n=20, mode="touch|cross_below"),   # 事件定义（唯一，骨架单变量）
  context_filter: regime_bull@1(benchmark=510500.SS,   # 样本条件过滤：牛市 regime
                 rule="close > MA200"),                #   ——这类研究的关键在条件，
  universe: single(510500.SS) | liquidity_default,     #   不在事件；单标的/全池均可
  horizons: [5, 10, 20, 40],
  path_stats: [time_to_recover, mae, mfe],             # 演绎分析：恢复时间分布、
  transition_matrix: false                             #   事件后最大不利/有利偏移
}
```

- 证据：①定点：事件后 N 日收益均值/中位数/胜率，**减无条件分布同窗口径
  的差值**；②路径：恢复时间（回到事件前价的天数分布）、事件后 MAE/MFE；
  ③可选迁移矩阵（事件状态 → 后续状态）；
- `context_filter` 是研究问题的定义（样本选择口径），不算第二个自由变量——
  但同一事件换条件 = 另一个实验（各自独立入链，结论可对照：
  "牛市跌破 vs 熊市跌破"自然成为一对实验）；
- 判定建议：差值的符号与假设一致且超过噪声带（按事件数 bootstrap）→
  confirmed；反号 → rejected；
- 注意：event_study 的 confirmed 只表示"含信息"，不代表"能赚钱"——
  那是 backtest 实验的事（§6.1.3 路径）。

#### 6.5.3 `bucket_analysis`

- 证据：M 组（默认 5）各组前瞻收益、单调性（相邻组符号一致的占比）、
  Q1−Q5 利差；对照 = 同一批信号日随机打乱分组的重算结果；
- 判定建议：单调且 |Q1−Q5| 超随机带 → confirmed；倒挂 → rejected（方向
  反了本身也是结论，记 reasoning）。

#### 6.5.4 `distribution`

- 证据：池化分布的均值/σ/偏度/分位数表、按类型×周期分组对比；
- 判定：不对"有效性"下结论，verdict 固定 inconclusive 一档 + 标定建议
  （如"±9 使无趋势占比 63~69%，与日 ±5 语义对齐"）；
- 用途：为模块参数（阈值类）提供取值依据，存台账供后续实验引用。

### 6.6 纪律流水线的工程实现（泛化版）

#### 6.6.1 创建校验（入口卡控）

共性五条（骨架强制）：

1. hypothesis 非空且 ≥ 最小长度；
2. 对照可声明（评估模块注册表中存在且 spec 过该模块 schema）；
3. 单变量可判定（spec 中自由变量数 = 1，由模块 schema 机器检查）；
4. 引用合法（策略版本已冻结 / 模块已注册且为 reviewed 态 / 参数域内）；
5. attempt_index 平台赋值。

per-module 追加：backtest 改进型实验的 diff 恰一槽（多槽须 is_compound +
compound_reason，串行链优先的提示照出；**创建型实验 base=blank-base
豁免，平台自动识别**，见 §6.1.4）；event/bucket 的事件定义恰一个。

#### 6.6.2 对照与证据平台生成

基准同窗重跑（backtest）/ 无条件分布同窗计算（event）/ 随机打乱重算
（bucket）——全部由平台执行，不接受创建者自报的对照数字。

#### 6.6.3 平台自动警告（warnings_json，继承被删研究的"共同局限"）

- 事件/样本数过少（< 阈值）；
- 前瞻窗口重叠率高（同一标的相邻事件 < N 日）；
- 截面相关（事件集中于少数交易日/板块，独立赌注数 ≪ 名义 N）；
- 单一 regime（样本全落在 SMA200 同一侧）；
- 幸存者偏差未消除（universe 为当前池穿越历史时，必带）。
  警告不阻断实验，但进 verdict 永久展示——让读结论的人/AI 自己打折。

#### 6.6.4 holdout 工程化（对全部评估模块生效）

- sample/holdout 窗口全局配置（首版 sample=[2020-01-01, 2024-12-31]）；
- 任何评估模块取数窗口超 sample → 需 holdout_token（人审放行）+ 计数 +
  holdout_touched 记录；高原补跑、随机对照重算同样受限。

#### 6.6.5 尝试计数与显著性校正（DSR 版，2026-09-22 审计 A 项接纳）

- `subject_key` 标识研究线：backtest = base 策略 id；event/bucket =
  信号模块 name；distribution = 指标 name；
- attempt_index = count（同 subject_key 的实验）+1，作为 DSR 的试验
  次数输入（原"阶梯收紧表"废除——DSR 公式比自拍阶梯更有依据）；
- **verdict 直接计算 PSR/DSR**：PSR = Sharpe 超越基准的概率（Bailey &
  López de Prado 2012）；DSR = 按尝试次数、样本长度、收益偏度/峰度
  校正的 Deflated Sharpe（2014）。confirmed 建议以 DSR > 0（且 PSR 超
  阈值）为准；附 **MinTRL**（最小可信样本长度）展示件；
- 二期纳入：PBO（回测过拟合概率）、按研究线定期 FDR（BH 校正）。

#### 6.6.6 重复检测

同 evaluation_module + 同 subject_key + spec 相似（参数容差内）→ 列出
历史实验（含失败）要求确认"非重复发现"；确认后允许创建。

### 6.7 权限模型、沙箱边界、服务面

**权限**：

- append-only：各表代码层只有 insert/select + 库层触发器拒 UPDATE/DELETE；
- 写按 owner_session 隔离，读全开放（含他人失败实验）。

**沙箱边界（实验/策略之间的隔离保证）**：本系统的"沙箱"是逻辑隔离，
不是容器——隔离诉求是"结果不受干扰、记录不被篡改"，而模块入库过
自动测试门、无任意代码执行，容器级隔离的成本远超收益。五层保证：

1. **数据隔离**：每次运行经 gateway 以各自声明的 as_of + data_version
   锚定取数；行情库只读，实验无法写；
2. **运行隔离**：每 run 独立引擎实例/账户/面板副本，运行间无共享可变
   对象。跨 run 的只读缓存按内容键控（data_version + 窗口 + 符号 +
   模块版本）——不可变输入的缓存共享不破坏隔离语义，只是性能优化；
3. **状态隔离**：写入 append-only 且按 experiment/run/session 命名空间；
   策略版本不可变——别的实验改不了你的基准；
4. **并发隔离**：有界并发池（2~4 位），单 run 崩溃只影响自己
   （failed 入表）；每会话并发上限防霸占；多会话共用一池，FIFO；
5. **逻辑隔离**：声明式 spec + 参数域校验 + 模块自动测试门——
   AI 无任意代码执行路径。

若未来放开"AI 直接提交代码进运行路径"，再升级为容器/资源限制的真
沙箱——当前设计用不到。

**服务面（通道无关）**：

- 实验：propose_experiment / get_experiment / list_experiments /
  confirm_verdict / run_status；
- 课题：propose_topic / append_experiment_to_topic / conclude_topic（结论 +
  引用校验，见 §6.4.1）/ get_topic；
- 目录：list_modules / list_evaluations / get_strategy_version；
- 台账：search_ledger / strategy_line；
- 治理：propose_module（draft 即存即见；自动测试门通过即可执行，
  DSL 表达式免测，见 §6.2.2；人保留抽检与下架权）/ grant_holdout
  （仅 human session）。

AI 沙箱边界 = 这张清单：组合已审核模块提实验 + 读台账 + 保存模块草稿；
不能让未过测试门的代码进运行路径、不能改判定规则、不能碰 holdout、
不能删改记录。

### 6.8 明确不做（本版）

- 工业化因子生产全部（DSL/因子库/IC 流水线）；
- 台账 Web 看板 UI（阶段 5 后）；
- 分布式实验（单机并发池足够）；
- verdict 判定阈值的自动调参（人工定入配置，调整走架构稿修订流程）；
- 新增评估模块（本版四个封顶，新形态来了先吵清楚再注册）；
- 策略组合 / 策略级轮换（meta-portfolio：多策略排名、资金在策略间分配，
  Alvarez 式策略轮换——§6.9.4 抽样发现的已知场景缺口；当前对象模型只有
  "策略→持仓"一层，需要时作为 L3 之上的新对象立项，不破坏现有范式）；
- 组合优化类 sizing（稳健优化/风险分解/反向优化：注册新 sizing 模块即可，
  范式不破，但需协方差估计与优化器依赖，排在"等风险够用"之后）。

### 6.9 示例

#### 6.9.1 被删的七项研究在新范式下的呈现

| 归档研究 | 评估模块 | spec 要点 | 对照 | verdict（以当年结论回填） |
|---|---|---|---|---|
| 趋势值全市场分布 | `distribution` | {metric: trend_score@v3, group_by: [asset_type, period]} | 判断准则"无趋势占比 60~70%" | inconclusive（固定档）+ 标定建议"±5 保留" |
| 相位迁移 v1（周期收盘口径） | `event_study` | {event: phase_combo@1, horizons: [5,10,20,40], matrix: true} | 无条件收益分布 | confirmed（负负负 > 正正正）——**后被链上后续实验修正** |
| 相位迁移 v2（在途合成口径） | `event_study` | {event: phase_combo@2（在途合成）, 同上} | 同上 | confirmed 但效应腰斩——口径缺陷暴露 |
| 相位迁移 v3（滚动锚定口径） | `event_study` | {event: phase_combo@3（滚动锚定）, 同上} | 同上 | **rejected**（旗舰路径衰减至 +2.6%/55%，否定为独立信号） |
| 滚动趋势标定 | `distribution` | {metric: rolling_trend w/m} | 判断准则"与日 ±5 语义对齐" | inconclusive + 标定建议"周/月 ±9" |
| 相位迁移 v4（th9） | `event_study` | {event: phase_combo@4（th9）, 同上} | 同上 | confirmed（正负负结构最强），迁移表定位为先验 |
| 组合层研究 | `bucket_analysis` × N + `portfolio_backtest` 链 | 见下方走查 | 随机打乱 / 基准策略 | 见下方走查 |

两个关键叙事，正是新范式要保障的东西：

- **v1→v4 是"串行实验链 + 模块版本化"的范例**：四次实验是同一事件定义
  模块的四个版本（`phase_combo@1..4`，口径演进 = 模块版本演进，防止"同名
  不同义"），`parent_experiment_id` 串成链。v1 的明星结论（负负无→负负负
  +10%/77%）被 v3 亲手否定——旧体系里这条纠错链靠研究者记忆维系，
  新范式下它完整留痕、血缘可追，且每一步的口径缺陷（周期收盘滞后、
  在途合成量能阻尼）都写在当次实验的 reasoning 里。**失败实验同等入表**
  的价值在此实证：没有 v1 的 confirmed，就没有 v3 的 rejected 的可对照性。
- **组合层研究是两类评估模块的接力**：前半"候选口径/选股边际"是
  `bucket_analysis` 的一串单变量实验（feature 分别为 days_since_signal /
  trend_strength / atr_pct，每次只换一个特征，对照随机打乱）；后半"持仓数
  sweep / breadth 闸门"是 `portfolio_backtest` 的串行链（slot_limit 参数
  5→10→15→20 四次单槽 diff；market_gate 模块增删 diff）。旧体系里这两半
  混在一个研究报告里，新范式下它们是各自独立、可单独复验的实验记录。

#### 6.9.2 机构/论文常规实验的 fit 检查

以调研文档附录 A 的来源清单为锚，逐一检查"常规、不太复杂、有价值"的
实验能否落入四个评估模块：

| 实验 | 出处 | 评估模块 | spec 一句话 | fit |
|---|---|---|---|---|
| 唐奇安 N 日突破有没有料 | 海龟【经验】 | `event_study` | event=channel_breakout@1(N=55/20) | ✅ |
| 52 周新高事件前瞻收益 | George & Hwang 2004 JoF | `event_study` | event=high_52w@1 | ✅ |
| 绝对动量转正（双动量） | Antonacci 2015 | `event_study` | event=abs_momentum@1(ret12m>0) | ✅ |
| MA/MACD 交叉前瞻收益 | 经典 | `event_study` | event=ma_cross@1 / macd_cross@1 | ✅ |
| 12-1 截面动量（跳过最近月） | Jegadeesh & Titman 1993；Novy-Marx 2012 | `bucket_analysis` | feature=mom_12_1 | ✅ |
| A 股月度反转检验 | 王永宏&赵学军 2001 | `bucket_analysis` | feature=ret21，预期**倒挂** | ✅ |
| 波动调整动量 ret20/atr_pct | 经验 | `bucket_analysis` | feature=vol_adj_mom | ✅ |
| 52 周新高距离作截面特征 | George & Hwang 2004 | `bucket_analysis` | feature=dist_52w_high | ✅ |
| 低波动异象 | Baker et al. 2011 | `bucket_analysis` | feature=atr_pct（预期倒挂或平） | ✅ |
| 趋势质量（ER / 斜率×R²） | Clenow 2015 | `bucket_analysis` | feature=er / slope_r2 | ✅ |
| 随机入场 + 移动止损（Van Tharp） | 【经验】 | `portfolio_backtest` | signal=random_entry diff | ✅（benchmark 策略即此） |
| 止损宽度/形态消融 | 自有 stop-width 诊断传统 | `portfolio_backtest` | position_risk 参数/模块 diff | ✅ |
| 波动率目标/动量波动管理 | Daniel & Moskowitz 2016；Barroso & Santa-Clara 2015 | `portfolio_backtest` | sizing=vol_target diff | ✅ |
| 大盘 regime 闸门（SMA200 上才开仓） | Faber 2007 TAA | `portfolio_backtest` | portfolio_risk 加 market_gate | ✅ |
| 槽位/组合热/集中度上限 | 海龟；Van Tharp | `portfolio_backtest` | 三 gate 参数 diff 链 | ✅ |
| 缓冲轮换 vs 持有优先 | Carver 2015；Clenow 带宽 | `portfolio_backtest` | execution=buffered_rotation diff | ✅ |
| 成本敏感性（滑点/佣金 ±） | Korajczyk & Sadka 2004 | `portfolio_backtest` | execution 滑点参数 diff | ✅ |
| 成交时点（开盘/收盘/尾盘） | 经验 | `portfolio_backtest` | execution=fill_policy diff | ✅ |
| ATR% 分布 → 止损倍数标定 | 经验 | `distribution` | metric=atr_pct | ✅ |
| 信号频率分布 → 槽位数标定 | 经验 | `distribution` | metric=signals_per_day | ✅ |

**fit 不了的边界（诚实标注，且都不是范式问题）**：

- 基本面因子（PE/PB/ROE/质量）：无财务数据源——数据范围问题，不是范式
  问题；数据源补齐后 `bucket_analysis` 直接可用；
- 严格 PIT universe 的动量复现：等阶段 7 指数成分历史/年度龙头池；
- 多空双腿/市场中性组合：`event_study`/`bucket_analysis` 不受影响，
  `portfolio_backtest` 受 MVP 不做空限制；
- 日内/高频：日频定位外；
- 均值-方差组合优化：范式不破——注册一个新 sizing 模块即可，但超出
  MVP，排在等风险够用之后。

结论：**日频、多头、事件驱动、趋势/动量家族的常规实验，四个评估模块
全覆盖**；覆盖不了的都有明确的非范式原因。

#### 6.9.3 完整走查：一个 MA20 金叉研究的一生

```
# 第一步：快筛（有没有料）
experiment #E101:
  evaluation_module: event_study@1
  subject_key: ma_cross@1
  spec: {signal: ma_cross@1(n=20), universe: liquidity_default,
         horizons: [5,10,20]}
  hypothesis: "MA20 金叉后 10 日前瞻收益显著高于无条件分布"
  → verdict: confirmed（Δ+1.8%，超噪声带；warnings: 事件集中于 2024 底
    共振日，截面相关警告 ×1）

# 第二步：做成策略验证（赚不赚钱）
experiment #E114:
  evaluation_module: portfolio_backtest@1
  subject_key: strategy/base-v1
  spec: {base: base-v1@3, diff: [{slot: signal,
         from: macd_cross@1, to: ma_cross@1}]}
  hypothesis: "ma_cross 替换 macd_cross 后 ΔSharpe > 0"
  parent_experiment_id: E101        # 血缘挂快筛证据
  → verdict: rejected（ΔSharpe −0.11，高原补跑 peak，regime 拆分显示
    恶化集中于 SMA200 下段）reasoning: 信号太密，震荡市被反复打脸

# 结果：E114 作为失败实验留档。半年后另一个 AI 会话提出类似假设时，
# 重复检测命中 E101/E114，先读到"为什么被否"，而不是再烧一遍算力。
```

若第二步 confirmed：策略版本 `base-v1@4`（signal=ma_cross@1）入库，
血缘挂 E101+E114 两级实验——这就是 §6.1.3 路径的完整实例。

#### 6.9.4 外部内容源抽样：映翡量化（InfinityQuant）的 fit 检查

抽样：BNP《主动+被动基金多资产稳健优化框架》解读、Cesar Alvarez 访谈
（Connors Research 前策略总监）两篇全文 + 账号定位（国际量化论文解读 +
实践者访谈）。结论：思路绝大多数 fit，另照出两个真缺口。

**直接 fit 的思路**：

| 思路 | fit 位置 |
|---|---|
| "均值回归不止损反而最好"的反直觉发现 | `portfolio_backtest`：position_risk 槽 stop ↔ none 消融 |
| 参数敏感性 ±10~20% 扫数千次、偏离均值 1σ 即过拟合 | 高原补跑（§6.5.1）——其"标准差检查"应并入 plateau 判定 |
| 双动量战术配置（动荡期持币） | `market_gate` + `event_study`（绝对动量转正） |
| 定期审查"回测 vs 实盘一致性" | 实盘运行器对账（§5.7） |
| "关注退出和排名，而不只是进入" | rank 槽 + position_risk 槽的印证 |

**缺口一：策略组合 / 策略级轮换（meta-portfolio）。** Alvarez 维护 ~10 个
策略、按月/季排名、前 5 进实盘、一两年回不去就退役——管理对象是"策略的
组合"，而当前对象模型只有"一个策略 → 持仓组合"一层，没有"资金在策略间
分配"这个对象。这是本次抽样发现的最大场景缺口。不破坏范式（策略库已
版本化带血缘）：未来在 L3 之上加"策略组合"对象（输入多个入库策略、输出
资金分配与轮换规则）即可。本版不做，记入 §6.8。

**缺口二：组合优化类 sizing。** 稳健优化/风险分解/反向优化（BNP 式）的
fit 路径 = 注册新 sizing 模块，范式不破，但需要协方差估计与优化器依赖，
远超 MVP，排在"等风险够用"之后。

**不适配边界**（用户明示可接受）：期货特有机制（跨期/展期/杠杆/做空双腿）
——MVP 不做空、无期货数据；但 CTA 趋势思路（时序动量）完全 fit，本就是
主家族。

#### 6.9.5 外部内容源抽样二：卖方策略号与投资人观点号

抽样：晨明的策略深度思考（广发策略团队，卖方策略研究：《6 轮牛市 99 次
考验 20 日均线后如何演绎》、行业周期阶段盘点等）；投资作业本Pro（知名
投资人/分析师观点访谈：洪灏、李蓓、达利欧、段永平等）。

**定位结论：观点性内容是"假设的来源"，不是"证据的来源"。** 骨架第 1 条
（假设先行）天然欢迎外部观点，但任何观点必须翻译成可证伪的 spec 才能进
台账——"资金从过热板块流向过冷板块"不是结论，是一条待检验假设。

**卖方策略号的典型形态「历史 N 次 X 之后市场如何演绎」= `event_study`
的直接用例。** 且卖方此类研究的方法论缺陷恰好被本范式克制：惯例上只讲
事件后平均涨跌幅、**不做无条件对照**、样本少且 regime 单一、叙事驱动
选样本——骨架第 2 条（对照强制）+ §6.6.3 平台警告（样本过少/单一 regime）
正是针对这些缺陷。这是"平台纪律优于卖方惯例"的实证场景。

可转译方向的 fit 检查：

| 观点/内容 | 转译为假设 | 评估模块 |
|---|---|---|
| 牛市中 99 次考验 20 日均线（晨明） | 牛市 regime 跌破 MA20 后的前瞻收益/恢复概率 | `event_study` |
| 行业周期阶段盘点（晨明） | regime 分类口径 | `distribution` / market_gate 输入 |
| 资金从过热板块流向过冷板块（洪灏） | 板块温度高分组后续跑输低分组（板块层反转） | `bucket_analysis`（注：旧研究曾撤回"bias_atr 过热否决"，可用标准分桶重检） |
| 杠铃配置：矛（科技）+ 盾（黄金/红利） | 风格配额优于纯集中度上限 | `portfolio_backtest`（concentration 变体） |
| 牛市阶段划分/局部泡沫（李蓓） | regime 标注 | verdict regime 拆分素材 |
| 黄金/红利的防御属性 | 大盘下跌段避险 ETF 相对收益为正 | `event_study` → market_gate 避险模块素材 |
| 宏观周期叙事、个股逻辑、一级市场 | 不可证伪 / 无数据 | 边界：只能当假设来源，大多数连假设也当不了 |

**边界重申**：观点号的大量内容（宏观叙事、个股逻辑、定性判断）落在
范式外——这不是范式缺陷，而是"不可证伪的内容本来就不该进研究体系"。
可证伪化的部分，四个评估模块已够用。

### 6.10 业界对标审计

按"已对齐 / 业界通用但缺失"两档审计（投研层无有意偏离项）。

#### 6.10.1 已对齐（业界/学界通行做法）

- 假设先行（pre-registration 思想）、对照强制、结论取差值；
- 样本内/外切分 + holdout（业界标准）；
- 实验台账 append-only + 全血缘（MLflow/W&B 式实验追踪的对等物）；
- 尝试计数 + 显著性折扣（多重检验意识，Bailey & López de Prado 一系）；
- IC/分桶快检（因子验证标准件——工业化部分推迟，范式内）；
- 策略孵化期（阶段 4 并行月，业界 paper trading 惯例）。

#### 6.10.2 业界通用但本设计缺失（已定结论）

| # | 业界做法 | 说明 | 结论（2026-09-22 用户确认） |
|---|---|---|---|
| A | **Deflated Sharpe Ratio / PSR**（Bailey & López de Prado 2012/2014） | 按尝试次数、样本长度、收益偏度峰度校正 Sharpe，是多重检验校正的金标准；本设计此前是自拍的"attempt 阶梯收紧" | **接纳**：DSR/PSR 公式现成且比阶梯表有依据，verdict 里直接计算，已替换阶梯表（见 §6.6.5） |
| B | **PBO**（回测过拟合概率，CSCV） | DSR 姊妹指标，估计"样本外 Sharpe 为负"的概率 | **随 A 接纳（二期**，计算成本略高） |
| C | **MinTRL/MinBTL**（最小可信样本长度） | DSR 姊妹指标：当前 Sharpe 需要多长样本才可信 | **随 A 接纳**（verdict 展示件，廉价，见 §6.6.5） |
| D | FDR（Benjamini-Hochberg） | 对一批实验的 p 值做错误发现率校正（台账层面） | **二期接纳**：AI 批量实验铺开后，按研究线定期做 BH 校正 |
| E | Walk-forward 滚动样本外 | 同 §5.12.3 审计 F 项（跨层同一项） | **接纳（二期）**，见 §6.5.1 |
| F | Purged/embargoed CV（净化交叉验证） | López de Prado 的 ML 验证标准 | **暂不**：无 ML 场景；因子挖掘启动时再评 |
| G | White's Reality Check / SPA | 多重检验校正的早期经典 | **不接纳**：已被 DSR 一系取代 |

#### 6.10.3 口径声明（不需决策，仅明示）

- 实验对照 = 单一基准策略（算 deltas）；报告 benchmark 展示 = 多选——
  两个概念已在 §5.4.3 区分；
- verdict 的建议规则由平台持有、阈值入配置（§6.6），调整走架构稿修订
  流程——因为它本身决定所有实验的置信度。
