## 总体评价

这是一份质量很高的设计方案。结构清晰、决策链路完整、备选方案与权衡记录充分。方案在「简单可交付」与「扩展性预留」之间拿捏得当——串行单线程、分层存储+钻取重跑、4 个解耦视图、不做统计检验，这些取舍都是务实的 MVP 选择。

## 一、关键问题（建议在实施前处理）

### 1.1 🔴 钻取重跑使用了「当前策略」而非「批次快照」——结果不可复现

**原文**（§2 决策 #7）：
> 点某一格 → 跳转现有单标的回测页**实时重跑**

**问题**：现有 `market_view.html` 的单标的回测走 `StrategyLoader.load(strategy_id)`，它读取的是**数据库当前版本**的策略。如果用户在批次跑完之后编辑了策略，钻取重跑就会用新策略而非批次快照，结果对不上。

**建议**：钻取跳转时把批次快照中的策略 JSON 作为参数传入（URL query 带 `strategy_snapshot=base64json` 或走 sessionStorage），回测页检测到快照参数时跳过 `StrategyLoader`，直接使用快照 JSON 构造 `RuleBacktestRequest`。

**或者更简单**：钻取不走跳转，直接在批次页内通过 API 实时重跑（后端从 `batch_backtest_runs.strategy_snapshot_json` 取快照执行，返回完整瘦身结果）。这样还避免了 `market_view.html` 的改造。

### 1.2 🔴 策略快照的粒度：是否需要快照 `indicator_config` 的依赖？

策略 JSON 中包含 `indicator_config`，它引用指标的参数（如 MA 周期）。这些指标定义在 `rule_backtest/indicators.py` 中，如果未来指标实现变了（如修改 MA 计算逻辑），即使策略快照 JSON 不变，重跑结果也会漂移。

**建议**：这是一个「已知接受」的代价，但应该在文档和 UI 中明确其范围——「快照保证策略参数不变，不保证底层指标实现不变」。如果未来对此有硬要求，可考虑记录引擎版本号（git commit hash）到批次行。

### 1.3 🟡 `batch_backtest_cells` 缺少索引设计

1600 行不算大，但未来如果扩展到全标的池（716 × N 策略），`cells` 表查询会需要索引。建议至少预留：

```sql
CREATE INDEX idx_batch_cells_batch ON batch_backtest_cells(batch_id);
CREATE INDEX idx_batch_cells_symbol ON batch_backtest_cells(symbol);
CREATE INDEX idx_batch_cells_strategy ON batch_backtest_cells(strategy_id);
-- 分析视图常用排序列：
CREATE INDEX idx_batch_cells_annual_return ON batch_backtest_cells(batch_id, annual_return);
```

实施阶段按「先不加，发现慢再加」也可，但设计文档应提及。

### 1.4 🟡 单批次最长 25 分钟的可靠性隐患

**问题**：后台线程跑 25 分钟期间，如果服务重启（部署、OOM、异常），批次中断。方案 §6.4 说「cells 已落库的部分保留，批次标为 error，可重跑」，但没有**断点续跑**机制——重跑意味着从头再来，浪费已完成的计算。

**建议**：MVP 可以不做断点续跑，但至少做到：
- 每格完成后**立即**写库（commit），不攒在内存里等批次结束——方案已隐含此意，建议在 `batch_service.py` 设计中明确写出「逐格 commit」。
- `status=running` 的批次在服务启动时自动标为 `error`（或 `interrupted`），避免遗留僵尸批次。
- 在 UI 上对 `interrupted` 批次提供「续跑」（resume）按钮——虽然是 V2 功能，但设计上预留 `status=interrupted` 枚举值。

### 1.5 🟡 标的特征计算时机

方案 §5.3 中 `symbol-features` API 是一个独立端点，暗示它在请求时实时计算。但标的特征（波动率、动量、趋势度）依赖全量行情数据，264 个标的逐个计算可能耗时数秒到数十秒。

**建议**：标的特征在**批次执行时一并计算并写入 cells 表**（增加 `volatility`, `momentum`, `trend_score`, `bh_return` 等列），`symbol-features` API 直接从 cells 读。这样：
- 分析视图加载快（无需等待计算）
- 特征与回测区间一致（都基于同一段 bars）
- 散点图和分桶视图直接用 cells 数据，不需要额外 API

### 1.6 🟡 超额收益定义需明确方向

方案 §7.2 问「策略年化 − B&H 年化」是否过度简化。从现有代码看引擎已计算 `benchmark`（buy_and_hold），`excess_annual_return` 可以直接从 summary 中提取。

**建议**：MVP 用简单减法即可，但需**明确符号方向**：`excess = strategy_annual_return - benchmark_annual_return`，正值表示跑赢买入持有。在 UI 中标注清楚，避免用户误读。

## 二、设计优化建议

### 2.1 分层存储边界微调建议

方案 §3.1 的分层边界（存 summary + annual + monthly + trades，不存 daily_nav/K 线/condition_trace）合理。一个补充建议：

- **考虑存「月度采样的 NAV」**（每个自然月最后一个交易日的净值）。12 个月 × N 年 = 几十个数据点，体积可忽略，但能支撑策略间净值曲线叠加对比——这是用户理解「策略 A vs 策略 B 在同一标的上表现差异」的核心可视化。完整 daily_nav 确实太重，月度采样是很好的折中。

### 2.2 执行顺序优化可更细化

方案 §3.4.5 提到「按标的分组，每标的只加载一次行情」。可以进一步优化：

```
for symbol in symbols:
    bars = MarketStore().load_history(symbol)
    if len(bars) < MIN_BARS: 标记整标的 cells 为 skipped; continue
    # 预计算：instrument_type、start_date、end_date
    for strategy in strategies:
        try:
            result = engine.run(RuleBacktestRequest(..., bars=bars, sizer=None))
            write_cell(result)
        except Exception:
            write_cell(status=failed, error=...)
```

这样每个标的只做一次 IO + 一次 instrument_type 解析。方案已隐含此意，建议在 `batch_service.py` 伪代码中显式写出以指导实现。

### 2.3 `data_end_date` 的确定方式

方案提到 `data_end_date` 作为时效提示，但未说明它如何确定。

**建议**：取 `market_data_qfq` 中**所有涉及标的的日期最大值**的公共部分（即 `SELECT MAX(date) FROM market_data_qfq WHERE symbol IN (...)`），而不是每个标的各自的最后日期。这样整个批次的「数据截止日」一致，UI 展示清晰。

如果中途行情更新（批次运行到一半时 16:30 增量更新触发），已跑完的标的用旧数据、未跑的用新数据。这是一个已知的不一致窗口，在 `data_end_date` 上标注「批次执行期间数据可能混合两日」即可，不必过度设计。

### 2.4 API 端点小修

- `GET /batch-backtest/api/runs/{batch_id}/cells` —— 建议加 `?sort=annual_return&order=desc&limit=200` 参数，明细大表排序走后端（SQL `ORDER BY`），避免前端对全量做排序（1600 行还好，但养成好习惯）。或者如果确定前端排序无性能问题，可维持现状，但文档中应注明。
- `GET /batch-backtest/api/runs/{batch_id}/cell?symbol=&strategy_id=` —— 建议改为 `.../cells/{symbol}/{strategy_id}` 以更 RESTful，但现有 query param 风格也 OK。

### 2.5 前端「钻取改造」方案细化

方案 §5.4 提到 `market_view.html` 改造支持 URL query 预填。考虑到 §1.1 的策略快照问题，建议改为**批次页内嵌钻取**：点击单元格 → 在批次页的一个侧边面板 / 模态框中展示完整回测结果（调用后端 API 用快照重跑），无需跳转到 `market_view.html`。这解决了快照一致性，也避免了跨页面状态传递的复杂性。

如果坚持跳转方案，至少需要把快照 JSON 传过去，`market_view.html` 需新增「快照模式」。

### 2.6 前端明细大表性能

1600 行 × 15+ 列，全部渲染到 DOM 可能有性能压力。建议：
- 使用**虚拟滚动**（或起码分页）渲染表格体
- ECharts 散点图点数量 1600 个无压力；热力图矩阵也很小

### 2.7 测试补充建议

除方案 §5.5 列出的单测和 API 测之外，建议加一个**小规模端到端 smoketest**：
- 选「商品」类目（5 个标的）× 1 个策略 = 5 格
- 完整走一遍：创建批次 → 执行 → 查 cells → 钻取重跑 → 删批次
- 这个测试可以做成脚本，也可以做成 pytest fixture

## 三、开放问题回应（§7）

### 3.1 分层存储边界是否合理？

**合理**。trades + annual + monthly 足以覆盖复盘诉求。唯一建议补充的是**月度采样 NAV**（见 §2.1），成本极低但使用价值高。

### 3.2 超额收益定义

MVP 用「策略年化 − B&H 年化」没问题。alpha/beta 回归需要基准指数（如沪深 300），且对单个标的做回归样本量有限（月度收益 N = 年数 × 12，早期标的可能有 200+ 个月，足够做简单线性回归）。建议列为 V2 增强项，不在 MVP 引入。

### 3.3 特征分桶的特征选择

现有特征 + 建议补充：

| 特征 | 来源 | 成本 | 信息量 |
|---|---|---|---|
| 波动率（年化标准差） | bars.close.pct_change().std() | 低 | 高 |
| 动量（N 日收益） | bars.close 收益率 | 低 | 高 |
| 趋势度（trend_score 均值） | trend_daily 表 | 低（已有缓存） | 高 |
| B&H 最大回撤 | bars.close 回撤 | 低 | 中 |
| 日均成交额 | bars.amount.mean() | 低 | 中（流动性代理） |
| 上市天数（bar_count） | bars 长度 | 零 | 中（区分新老标的） |

建议 MVP 至少包含前 4 个，后 2 个作为可选项。

### 3.4 批次管理

**建议**：保留全部历史批次 + 手动删除。每批次几十 MB（以 1600 格计），SQLite 轻松承载。自动清理策略（如只保留最近 N 个批次）作为后续配置项。批次间演变对比是 V2 功能，本期不做但 DB 设计已支持（同一 strategy_id 跨 batch_id 查询即可）。

### 3.5 假规律防护 —— 具体建议

在不引入完整统计检验的前提下，建议在视图层加以下保护：

1. **样本量标注**：每个聚合值旁边标注 `(n=XX)`。
2. **最小样本阈值**：类目 × 策略格子中位数的 n < 5 时，该格显示灰色（不展示数值）。避免「商品类目 5 个标的跑出 80% 胜率」被当规律。
3. **永久信息横幅**：每个分析 Tab 顶部固定提示：
   > ⚠️ 本视图仅用于**描述性观察与假设生成**，非统计推断。样本量有限，多重比较下可能出现噪声"规律"，结论需经独立验证。
4. **热力图颜色饱和度与样本量挂钩**：n 越小颜色越淡（或透明度越高），从视觉上削弱小样本格子的冲击力。

### 3.6 执行架构

串行 15~25 分钟可接受。未来扩展建议：

- **预留接口而非实现**：`batch_service.py` 中将「逐标的循环」抽象为一个可替换的 executor，默认为串行 for 循环，未来可替换为 `ProcessPoolExecutor`（注意：多进程下 SQLite 写需要切换到队列 + 单 consumer 写库模式）。
- **按标的（而非按格）分片**：每个 worker 拿标的清单中的一个标的，负责该标的下的所有策略。这样 bars 天然在 worker 内部复用，且无跨 worker 的 bars 传递开销。GIL 对 pandas 的影响：pandas 底层很多操作（如 `.iterrows()`）释放 GIL？不，纯 Python 迭代持有 GIL。所以多线程无效，多进程才是正道。

### 3.7 取消语义

建议方案：

- 点击取消 → `cancelled` 标志置位 → 当前格子跑完后检查标志 → 停止循环
- 批次状态：`cancelled`（区别于 `completed` 和 `error`）
- 已完成 cells：正常展示（status=ok/failed/skipped）
- 未执行 cells：不插入行（不在 cells 表中出现），或插入 status=`pending` 行供 UI 区分
- UI 表现：
  - 进度条变灰，显示「批次已取消」
  - cells 表中只展示已完成的行
  - 提供「重新运行」（新建批次）按钮，预填原批次的类目和策略选择
- 建议不做「续跑」：语义太复杂（需要跟踪哪些格子没跑、哪些标的的 bars 可复用），MVP 重跑即可。

## 四、遗漏点补充

### 4.1 行情增量更新与批次执行的时间窗口冲突

每日 16:30 行情增量更新。如果用户在 16:25 启动了批次（目标类目 264 个标的），前 100 个标的用旧数据跑完，16:30 之后行情更新了，后 164 个标的用新数据。同一个批次内的结果存在**数据版本不一致**。

**建议**：
1. 批次开始时记录 `market_data_snapshot_date = MAX(date) FROM market_data_qfq` 作为批次级别的数据日期锚点。
2. 执行期间不重新查询 `MAX(date)`，直接用锚点日期截断 bars（`bars = bars[bars.date <= anchor_date]`）。
3. 这样保证批次内所有 cells 使用同一截止日的数据。锚点日期写入 `batch_backtest_runs.data_end_date`。
4. 如果 `MarketStore.load_history()` 本身已被增量更新影响（SQLite 中已有新日期数据），截断操作可以消除差异——只要不出现复权因子回溯修改（通常不会，复权因子只对历史生效）。如果复权因子也随增量更新变了，那确实无法完全一致，但这种情况极少且影响很小。

### 4.2 内存管理

`engine.run()` 返回完整结果 dict（含 daily_nav、condition_trace 等大字段），虽然最终不落库，但在格子的写入函数中 result dict 仍在内存中。1600 个格子的结果 dict 如果同时存在，内存可能会爆。

**建议**：`batch_service.py` 中每个格子执行完后立即提取所需字段（summary + trades + annual + monthly + skipped_buys），然后**显式 `del result`** 释放完整 dict。Python GC 通常能及时回收，但显式释放是防御性编程。同时也是对每格 commit 的配合——commit 后 result 就可以丢弃了。

### 4.3 短数据标的的 MIN_BARS 门槛

方案 §3.4.3 提出 MIN_BARS=60。这个值需要验证：
- 日线 60 根 ≈ 3 个月（约一个季度），对于趋势跟踪策略，3 个月的数据量是否足够产生有意义的回测？取决于策略中使用的最大 lookback 指标（如 MA 200 需要 200 根 warmup）。引擎中的 `ValueResolver` 处理 NaN 的方式需要确认——如果指标因 warmup 不足返回 NaN，条件引擎的行为是什么？
- **建议**：MIN_BARS 取 60 和 `max_lookback` 的较大值，`max_lookback` 从策略快照的 `indicator_config` 中自动提取。或者更简单：MIN_BARS=60 不变，但在 cells 中额外记录 `bar_count`，分析视图中过滤掉 bar_count 过低的格子。

### 4.4 交易日历依赖

方案中没有提到交易日历。批量回测涉及 700+ 标的的日期范围计算，尤其是「截到上一交易日」这个操作，需要一个交易日历。

现有系统中可能已有交易日历（`market_data_qfq` 中的 distinct date 可作简易日历）。建议：
- 上一交易日 = `SELECT MAX(date) FROM market_data_qfq`（标的不重要，整个表的最新日）
- 不需要引入独立交易日历库

### 4.5 费率配置按 `asset_type` 区分的实现

方案 §5.2.5 提到「股票印花税 0.001 按 asset_type」。现有 `BacktestExecutionConfig` 中已通过 `instrument_type` 区分 etf/stock（股票有 `stock_stamp_tax_rate=0.001`）。批量执行时需根据 `instrument_metadata.asset_type` 映射到 `InstrumentType`（stock→stock, etf/债券/商品→etf），然后构造对应的 `BacktestExecutionConfig`。这是在 `batch_service.py` 中的细节，建议在设计文档中明确映射关系。

### 4.6 策略中 `sizer=None` 的兼容性

方案 §2 决策 #4 说「`position_strategy_ids=[]` → sizer=None → all-in，现有逻辑零成本支持」。从 `engine.py` 和 `models.py` 看确实如此——`RuleBacktestRequest.sizer` 默认为 None，`PositionSizer` 为 None 时走现有的 all-in 逻辑（`PositionState` 直接全仓买卖）。这一点确认无误。

### 4.7 批次名称的默认生成

方案 §5.1 中 `batch_backtest_runs.name` 是用户可命名的。建议默认名称为 `"{类目摘要} × {策略数}策略 - {日期}"` 如 `"股票(264) × 6策略 - 2026-07-26"`，用户可改。

## 五、总结

| 类别 | 数量 | 关键项 |
|---|---|---|
| 🔴 关键问题 | 2 | 钻取重跑策略快照一致性、策略依赖指标实现的隐式漂移 |
| 🟡 设计优化 | 5 | 索引缺失、断点续跑预留、特征计算时机、超额收益定义方向、批次数据一致性窗口 |
| 🟢 开放问题回应 | 7 | 见 §3 |
| 📝 遗漏补充 | 7 | 数据版本一致性、内存管理、MIN_BARS 验证、交易日历、费率映射、sizer 兼容性、批次命名 |

**总体建议**：方案可以进入实施，但请先解决 §1.1（钻取重跑快照一致性）和 §1.2（策略依赖标注），这两个问题如果不处理，后续会产生用户可见的「结果对不上」困惑。其余优化建议可在实施过程中逐步纳入，不必阻塞启动。
