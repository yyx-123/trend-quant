## 总体评价

方案整体质量很高，结构清晰，边界明确（MVP 该做什么、不做什么有清晰界定），分层存储 + 钻取重跑的核心架构合理，备选方案权衡分析扎实。以下按严重程度排列评审意见。

---

## 🔴 严重问题（建议修改）

### 1. 耗时估算是乐观下限，未覆盖多类目组合场景

**原文**（§5.2）："股票类目 264 × 6 策略 ≈ 1584 格 × ~0.5s ≈ 15~25 分钟"

**问题**：这个估算只覆盖单一「股票」类目。UI 支持多选一级类目（§2 决策 #1），如果用户同时选「股票+行业+宽基」= 554 标的 × 6 策略 = 3324 格 ≈ **30~50 分钟**。若未来策略数增长（用户现可能已有 10+ 策略），单批次可能接近 **1 小时+**。

| 场景 | 标的数 | 策略数 | 格子数 | 预估耗时 |
|---|---|---|---|---|
| 股票 | 264 | 6 | 1,584 | ~13 min |
| 股票+行业+宽基 | 554 | 6 | 3,324 | ~28 min |
| 全选（含小类目） | 716 | 6 | 4,296 | ~36 min |
| 全选 + 10 策略 | 716 | 10 | 7,160 | ~60 min |

**建议**：
- 在 UI 发起区**预估耗时**（`total_cells × 0.5s` 实时计算）告知用户。
- 在 `config_json` 中预留 `max_cells` 参数，超出时提示分批执行。
- 考虑将 §7 开放问题 6 的「按标的分片 worker 抽象」从"未来考虑"提升为**架构预留**（接口层面保证 `run_batch(batch_id)` 可被外部调度，而非只能后台线程执行），以便后续无缝切换到多 worker。

### 2. 服务重启导致 running 批次中断无启动检测

**原文**（§6 Risk 4）："服务重启会中断 running 批次（cells 已落库的部分保留，批次标为 error，可重跑）"

**问题**：这只是一个风险提示，但没有对应的恢复机制。如果批次正在执行时服务重启，`batch_backtest_runs` 表中有条目停留在 `running` 状态——不会被自动标记为 `error`，前端会看到一个"永远 running"的批次。

**建议**：在 FastAPI 启动事件（或 lazy 检测）中增加逻辑：

```python
# app lifecycle startup
def mark_stale_batches():
    db.execute("""
        UPDATE batch_backtest_runs 
        SET status = 'error', error = '服务重启导致批次中断'
        WHERE status = 'running'
    """)
```

这只需几行代码，但能避免一个明显的 UX 问题。

## 🟠 中等问题（建议改进）

### 3. `symbol-features` 接口的成本未评估

**原文**（§5.3）：`GET /batch-backtest/api/runs/{batch_id}/symbol-features` → 标的特征（波动率/动量/B&H 回撤/趋势度）

**问题**：这些特征是对应**批次时刻**的计算，还是**实时计算**？如果是实时：
- 每个标的的波动率/动量需从 `market_data_qfq` 读取历史数据计算（几百标的 × 全量 K 线 = 可能几秒甚至十几秒）
- 与当前数据关联，而非与批次时刻的数据关联，可能导致特征与批次结果不匹配（特征用的是最新数据，而批次结果基于历史快照）

**建议**：
- 在批次执行过程中**顺带计算标的特征**写入 `batch_backtest_cells` 或独立特征表（`batch_backtest_symbol_features`），计算成本摊入执行流程。
- 每个标的只需算一次（不依赖策略），按标的缓存即可。
- 如果保留实时计算设计，必须加内存缓存（TTL 策略）和响应时间评估。

### 4. 缺少运行中拦截（同一时间只能跑一个批次）

**问题**：目前没有约束防止用户重复发起批次。如果用户在批次 A（25 分钟）运行时又点了运行按钮：
- 策略 A：第二个请求也成功启动后台线程，两个批次争抢 CPU 和数据库连接，**互相拖慢**。
- 更好的场景：同参数重复请求无意义。

**建议**：
- `POST /run` 接口增加 `status == 'running'` 检查，有运行中批次则返回 `409 Conflict` + 当前批次信息。
- 前端按钮在批次运行时 disable。
- （可选）在 `config_json` 中增加 `queue_mode` 预留队列调度扩展点。

### 5. 超额收益定义的歧义需要收敛

**原文**：
- §7 开放问题 2："本期用「策略年化 − 买入持有年化」" 
- §5.1 平铺列：`excess_annual_return`

**问题**：超额收益可以有多种计算口径（简单减法 vs 回归 alpha vs 超额收益的夏普比率）。当前只有 `excess_annual_return` 一列，但不同视图可能需要不同口径：
- 明细大表：可能会同时想看「简单超额」和「风险调整后超额」
- 热力图如果只用简单超额，可能被极端值影响

**建议**：
- **在方案中选定并锁定定义**（MVP 用 `strategy_annual_return - benchmark_annual_return` 可以，但要写明），不要留作开放问题悬空。
- 考虑增加 `excess_calmar` 或 `return_risk_ratio` 作为辅助指标，让「风险调整后超额」也有体现。

### 6. 批次存储膨胀的估算需要更严谨

**原文**（§3.1）："1600 格估计几十 MB，SQLite 无压力"

**问题**：这个估算偏乐观。假设典型场景：
- `trades_json`：每格平均 30 笔交易，每笔约 150 字符 JSON → 4.5KB
- `monthly_heatmap_json`：每格约 600 字符 → 0.6KB  
- `annual_returns_json`：每格约 400 字符 → 0.4KB
- 指标平铺行本身 ~200B

单格合计约 **5.7KB**。716 标的 × 6 策略 ≈ 4,296 格 → **~24MB**（不含索引和 SQLite 页内碎片）。如果用户选择全类目 + 10 策略 → **~50MB+**。

虽然 SQLite 确实扛得住，但：
- 前端 `/cells` 接口返回全部格子（不含 blob）的响应体大小需关注（4,296 行 × 约 200B 指标列 ≈ **860KB** JSON）。
- "几十 KB" 的描述改为 "每格约 **几 KB 到几十 KB（含逐笔交易时）**" 更准确。

## 🟡 建议优化（低优先级）

### 7. 缺少最小样本量阈值的设计细节

**原文**（§3.3）提到统计警示但未在设计层实装。

**建议**：在视图层增加硬性防护：
- 热力图中某类目-策略组合少于 **N 个标的**（建议 N=5）的格子不显示数值或灰化。
- 散点图中 hover 显示样本量。
- 这些阈值在 `config_json` 或前端常量中定义，与提示文案一起落地，而非仅在文档中警示。

### 8. `/cells` 接口分页缺失

**原文**（§5.3）：`GET .../cells` → 全部格子维度+指标列

**问题**：全量返回在最大批次下可能有 **4,000+ 行**（参考 #6 估算 860KB），虽然 gzip 后不大，但前端渲染时一次性操作 DOM 可能卡顿。

**建议**：
- 后端从一次性全量返回改为**支持分页**（`?page=1&page_size=200`），前端视图自行管理聚合（热力图/散点/分桶可以等全量数据加载到 JS 内存后再渲染，但初始渲染可以先加载部分数据展示）。
- 或至少保留"全量返回"但加上 `Cache-Control` 头，避免重复请求。

### 9. 批次命名策略不明确

**原文**（§5.1）：`name` 字段但发起 API 中 `name?`（可选）

**问题**：
- 用户不填时用什么名字？自动生成规则是什么？
- 自动名建议：`{类目}_{策略数}策略_{日期}`（如 "股票_6策略_20260726"）

### 10. 单元测试覆盖范围的边界建议

**原文**（§5.5）：提到了测试文件

**建议补充下列测试场景**：
- 快照 JSON 发生 schema 变化后，历史批次反序列化兼容性
- `cancel` 在格子执行间隙的竞态测试
- `market_data_qfq` 无数据时（新标的）的 graceful 处理
- 引擎确定性测试——同 params 重跑是否产出相同 cells

## ✅ 值得肯定的设计点

1. **快照策略 JSON**（§3.4 #1）—— 这是方案中最关键的"可复现性"保障，很多项目会忽略。 
2. **按标的分组加载行情**（§3.4 #5）—— 避免重复 IO，工程素养好。
3. **失败隔离**（§2 #5）—— 单格失败 continue 而不是 abort 整个批次，对用户友好。
4. **视图零耦合**（§2 #8）—— 基于同一 cells 数据源的独立渲染，降低复杂度。
5. **启动前不跑/钻取重跑** —— 合理的 tradeoff，避免了一个复杂的状态管理问题。
6. **开放问题清单**（§7） —— 诚实标注未决策点，方便 reviewer 聚焦。

## 总结

**评审结论：方案核心架构合理，可进入实施，建议解决 #1（耗时预估展示）、#2（启动恢复）、#3（特征计算时机）、#4（并发拦截）四个问题后再开始编码。**

实施顺序建议微调：将起步检查（startup 标记 stale batch）作为第 0 步加入。
