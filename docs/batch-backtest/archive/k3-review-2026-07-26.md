## 0. 总体结论

**方案整体质量高，建议「有条件通过」。** 需求拆解清晰，关键决策（快照策略 JSON、分层存储 + 钻取重跑、失败隔离、视图零耦合）都踩在点上，备选方案权衡表也体现了真实的取舍过程而非走过场。§3.2 可比性问题、§3.3 统计警示的自我意识尤其难得。

但有 **4 处与代码现状不符的事实性断言** 需要修正（其中 2 处会影响设计），另有若干设计细节建议补强。以下按严重程度排列。

## 1. 需要修正的事实性错误（对照代码核实）

### 1.1 【重要】「引擎确定性 + golden-master 锁定」不成立，钻取重跑的漂移风险被低估

方案 §3.1 称「引擎是确定性的且有 golden-master 测试锁定一致性」，§2 决策 7 以此为钻取重跑方案的依据。核实结果：

- **没有端到端锁定数值的 golden-master。** `tests/unit/test_p13_memoized_golden.py:106-126` 锁定的是「memoized 路径 vs legacy 路径结果逐位一致」的等价性，不是固定数值；只有 `tests/unit/test_rule_backtest_metrics.py:113-147` 锁了 metrics 固定值。即：现有测试保证重构不改结果，**不保证跨日期重跑结果不变**。
- **存在跨日期非确定来源**：router 用 `date.today()` 截 end_date（`src/app/routers/rule_backtest.py:54-69` `_cap_end_date`），每日 16:30 行情更新会追加 K 线 → 隔日重跑同一参数结果必然不同（哪怕只差一天数据，买卖点和指标都会变）。方案 §6 风险 1 提了漂移，但措辞是「轻微漂移」「前复权因子变化」，**漏掉了最主要来源——数据每天都在变长**。
- 次要项：`random_uniform` 指标 seed=None 时用 OS 熵源（`src/rule_backtest/value_resolver.py:259-265`），虽 registry 标注「仅测试用」（`condition_engine.py:58`），但批量批次应显式拒绝含该指标的策略快照，否则格子结果不可复现。

**建议**：
1. 钻取重跑时，把批次记录的 `start_date/end_date` 显式传入请求（而不是让 router 用 `date.today()` 现截），这样只要行情历史不被改写，重跑结果与批次一致——**把漂移来源从「必然」缩小到「仅复权因子变化」**。这是对钻取链路的一个小而关键的改造，方案目前只写了「URL query 预填 symbol + strategy_ids + autorun」，应加上起止日期。
2. 补一个真正的端到端 golden-master：固定 symbol + 固定区间 + 固定策略快照，锁定 summary 数值。这对批量功能尤其重要——几千个格子落库后，任何引擎重构都应能回答「这批历史结果是否还可与现在重跑对比」。
3. 批次启动时校验策略快照不含随机指标。

### 1.2 【重要】「excess_annual_return 引擎已计算」不属实，需要新增

方案 §5.1 cells 表设计了 `benchmark_total_return, benchmark_annual_return, excess_annual_return` 平铺列，§3.2 称「引擎已计算 buy_and_hold 基准」。核实：

- buy_and_hold 基准确实存在（`src/rule_backtest/engine.py:223-227, 577-587`），但输出为嵌套的 `benchmark` / `benchmark_summary`，**顶层没有 `benchmark_annual_return`，全仓库无 `excess` 相关字段**（grep 无命中）。
- 影响很小（由 `summary.annual_return − benchmark_summary.annual_return` 派生即可），但方案应明确这是**批量服务层新增的派生计算**，而非现成字段，否则实施时会发现提取代码没东西可抄。
- 顺带提醒：基准是「首日满仓买入持有」（`engine.py:577-587`），在短生命周期标的上 B&H 年化波动极大，超额年化的横向可比性在短数据标的上会打折扣，与 §3.2 的可比性讨论叠加后，建议分析视图默认按 `bar_count` 过滤（见 §2.3）。

### 1.3 【中】market_view.html 目前不支持 URL query 预填

方案 §5.4 把「支持 URL query 预填」写成「小改」。核实：全文件无 `location.search`、无解析入站 query 的代码，唯一的 `URLSearchParams`（`market_view.html:1666`）是构造**出站**请求用的；标的选择靠页面内搜索框（`market_view.html:1652-1655`）。这不是「小改」而是「新增一条参数解析→预填→自动触发」的链路，工作量不大但应如实描述，且要和 §1.1 的起止日期透传一起设计。

### 1.4 【低】执行参数清单漏了 `fee_min=5.0`

方案 §5.2 列的参数（100000/0.002/0.0000854/100/印花税 0.001）均属实，但漏了 `fee_min=5.0`（`src/rule_backtest/models.py:26`，佣金按 `max(gross*rate, fee_min)` 收取，`engine.py:403,421,462`）。满仓 + lot_size=100 下，低价 ETF 单笔成交金额可能只有几千元，**最低 5 元佣金会使实际费率远超 0.0000854**，对高频交易策略的格子结果影响不可忽略。这不是要改参数，而是 `config_json` 快照必须包含 `fee_min`，且分析时应意识到小成价格子的费率口径不一致。

另核实确认无误的事实（供其他评审者参考）：sizer=None 满仓链路（`service.py:308-317`、`engine.py:329-330`）、内存结果 TTL 30 分钟（`rule_backtest.py:22-25`）、后台 daemon 线程模式（`rule_backtest.py:190-191`）、WAL 模式（`db.py:32-33`）、APScheduler 每日 16:30 更新（`src/core/scheduler.py:25-33`、`settings.py:70`）均与方案描述一致。

## 2. 设计层面的问题与建议

### 2.1 「每格约 0.5s」的耗时估算缺乏依据，而它是多项决策的地基

全仓库无任何性能基准/计时测试，「0.5s」仅出现在方案自身。而方案的多项关键决策都建立在这个数字上：

- 「串行 15~25 分钟可接受」→ 放弃并行（§4 备选表）；
- 「钻取重跑 0.5s 即可再生」→ 放弃全量落库（§4 备选表）；
- 「格子级进度粒度足够」（§3.4-4）。

注意 716 个标的中有约 7700 根 K 线的老股（§1.2），pandas 逐 bar 循环的耗时与 bar 数近似线性，**老股单格可能是 3~5s 而非 0.5s**，264 个股票类目若含较多长历史标的，批次时长可能冲到 40 分钟以上——这不会改变架构结论，但会影响「要不要预留并行接口」（开放问题 6）的答案。

**建议**：实施第 1 步前先跑一个 5 分钟的实测脚本：抽 20 个不同 bar 数量的标的 × 1 个策略计时，把耗时分布（而非均值）写回方案。如果 p90 单格 >1s，建议在 `BatchBacktestService` 的循环边界上预留「按标的分片」的接缝（哪怕本期不实现），成本只是一个函数签名。

### 2.2 取消机制是全系统首例，语义需要写细

核实：全仓库 grep `cancel`/`stop_event`/`threading.Event` 均无命中，本方案引入的协作式取消是**系统第一个取消机制**，没有先例可抄。方案只写了「每格间检查取消标志」，建议明确：

1. **取消的检查点在标的粒度还是格子粒度？** 单格 0.5s（或更久，见 §2.1），格子间检查足够；但「逐标的加载行情」本身也可能耗时（老股 7700 行），建议加载后也检查一次。
2. **取消后批次状态与 cells 的呈现**（开放问题 7 的答案建议）：批次置 `cancelled`，已落库 cells 完整保留且分析视图照常可用，明细表对未执行的格子**不显示**（而不是显示 failed）。`done_cells < total_cells` 本身就是取消的自然表达，无需额外状态。这要求分析视图统一只读 `status=ok` 的格子做聚合——建议写进 §5.4。
3. 后台线程是 daemon（现有模式），服务重启后 running 批次会变孤儿：方案 §6 风险 4 已提「标为 error」，建议落实为**启动时一次性把 `status=running` 的批次置为 `error`（注明 interrupted）**，否则孤儿批次永远显示 running。

### 2.3 skipped 语义的连锁影响没有贯穿到分析视图

MIN_BARS=60 记 `skipped` 是好设计（核实：现有引擎确实无门槛，数据非空就跑完，短数据靠指标 warmup 自然零交易——`indicators.py:37` 等返回 `insufficient_bars`、`condition_engine.py:74-79` None 比较一律 False）。但方案没有说明：**skipped/failed 格子在透视热力图和分桶视图里如何处理？** 中位数聚合若混入 0 交易的 ok 格（策略全程无信号也是 ok），和 skipped 格混在一起会污染分布。建议：

- 视图聚合只统计 `status=ok`；
- 热力图每格标注样本数 `n`，`n < 5` 的格子置灰——这也顺便回答了开放问题 5（假规律防护的最低限度措施）。

另外建议 MIN_BARS 不只按 K 线根数，还应提示「 warmup 后剩余 bar 数」：60 根 K 线对于含 SMA200 条件的策略依然全是 warmup，格子会是 ok 但零交易。可以在 cells 增加 `trade_count=0` 的标注或在视图中把零交易格子单独着色，帮助识别「策略在这个标的上根本没开火」。

### 2.4 批次与行情数据的版本对齐缺少一个低成本手段

方案记录了 `data_end_date`（好），但复权因子变化时历史 K 线会被改写，仅记录截止日无法发现「底层数据变了」。低成本加固：批次表加一列 `data_version`，取 `market_data_qfq` 的 `MAX(updated_at)`（或全表行数 + max(updated_at) 拼合），批次启动时写入。重跑钻取时若当前 data_version 与批次不一致，UI 提示「数据已更新，结果可能漂移」。一行查询的成本，把 §6 风险 1 从「盲信」变成「可检测」。

### 2.5 开放问题 2（超额收益定义）：MVP 用年化差值是对的，但要补一个口径说明

「策略年化 − B&H 年化」在 MVP 阶段足够，alpha/beta 回归属于过度设计（同意方案倾向）。但两点需要写明：

1. **口径不对称**：策略有费率/滑点/印花税摩擦，B&H 基准是否也扣费？（核实 `engine.py:577-587` 是首日满仓买入持有，需确认其是否扣首日买入佣金。）若基准无摩擦而策略有，超额会系统性偏低，横比时偏向「交易少的策略」——恰好在「策略-标的适配性」这个核心问题上引入偏差。建议确认口径并在 UI tooltip 写明。
2. 年化差值在短区间标的上极不稳定，建议散点图/分桶视图提供「超额总收益」和「超额年化」切换，短 bar_count 标的用前者。

### 2.6 小项

- **`symbol-features` 端点**（§5.3）：方案说特征含「波动率/动量/B&H 回撤/趋势度」，趋势度来自 `trend_daily`（字段核实：`trend_score/trend_ma5/trend_ma10/confidence` 等，`db.py:199-212`）。注意 `trend_daily` 主键含 `param_set`，取数时要明确用哪个参数组，否则特征值不唯一。波动率/动量建议直接从已落库的 cells 基准数据派生或按行情现算，避免再开一条数据链路。
- **cells 表主键**：`(batch_id, symbol, strategy_id)` 依赖快照里 strategy_id 稳定。若用户删除某策略后重建同名策略，id 变化不影响本设计（快照自带 id+name+payload），OK；但明细大表展示应优先用快照里的 `strategy_name` 而非联表现有策略表——方案已这么设计，强调一下别在实施时偷懒联表。
- **DELETE 端点**：删除批次应级联删 cells，且禁止删除 running 批次（或先取消再删），方案未写，补上。
- **导航**：`base.html` 加入口时注意批量回测是长时间任务，入口文案建议带「约 15~25 分钟」预期管理。

## 2. 纠正我自己第一轮的一处错误

我第一轮 §2.1 称「0.5s 全仓库无任何佐证」，**有误**：`README.md:47` 明确记载「典型趋势策略从 ~40-80s/次 降至 ~0.5s/次」。v1.1 在不采纳表中引对了出处，我接受这个纠正。同时注意到 README:47 自己就用「golden-master 锁定」指代那个等价性测试——方案 v1.0 的过度表述源头在 README，建议顺手把 README 措辞改准确（「新旧实现逐笔一致（等价性测试锁定）」），避免下一个人再被误导。

## 4. 实施级备注（非阻塞，实施时处理即可）

1. **409 并发保护需 DB 级**：两个同时到达的 POST /run 都通过「无 running」检查后各起一个批次。建议在建批次语句外包事务做 check-and-insert，或对 `status='running'` 建部分唯一索引兜底。方案只写了 409 语义，没写防竞态。
2. **伪代码的计数细节**：§5.2 中 skipped 分支 `continue` 在策略循环之外，需明确「写整标的 skipped 格」= 每个策略各写一行、且 `done_cells` 按格子数（非标的数）递增，否则进度条会在短数据标的上停滞。
3. **特征与 skipped 的顺序**：伪代码先 MIN_BARS 检查再算特征 → 短数据标的无特征行。§5.3 cells 端点的「join 特征表」必须是 LEFT JOIN，且视图对特征为 null 的标的降级（散点剔除/分桶归入「无特征」）。
4. **`engine_version` 的 git hash 兜底**：部署环境若非 git checkout，取 hash 会失败，需有 fallback（如 formula_version + 构建时间戳），别让建批次因此 500。
5. **sessionStorage 钻取的两个边界**：① 仅同源同标签页有效——从批次页跳转为同标签导航，成立；但若用户从批次列表「在新标签打开」则拿不到快照，market_view 快照模式检测到 drill=1 却读不到 sessionStorage 时需 fallback 到常规模式+提示，别白屏。② 快照 payload 数 KB，sessionStorage 5MB 限额无压力。
6. **伪代码冗余无害**：`bars[bars.date <= anchor]` 截断与 request 的 `end_date=anchor` 重复（引擎内部会再过滤一次，`engine.py:37`），保留截断版即可，少一次全量过滤。
7. **发起区耗时预估**按「格子数×单格耗时」会低估老股占比高的类目。低成本改进：`instrument_metadata` 有 `start_date`，可按标的 bar 数分两档（如 <1500 根按 0.5s、≥1500 根按 3s）估算，比单一均值准一个量级。等第 0 步实测分布出来后定档。
8. **取消标志的存放位置**方案未写：建议内存 `threading.Event`（与现有 `_rule_jobs` 模式一致）即可，不用落库——服务重启走 interrupted 路径，语义自洽。
