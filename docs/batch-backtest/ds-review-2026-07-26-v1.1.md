## 二、增量发现问题

### 2.1 🟡 sessionStorage 钻取链路：跨标签页失效

**问题**：§5.4 的钻取链路为「批次页写 sessionStorage → 跳 market_view → market_view 读 sessionStorage」。`sessionStorage` 在浏览器中的语义是**同源同标签页**隔离——如果用户通过以下方式打开链接，数据将丢失：

- 鼠标中键点击（新标签页打开，Chrome/Firefox 默认行为）
- Ctrl/Cmd + 点击
- 右键 → 在新标签页中打开
- `<a target="_blank">`

**影响**：用户在新标签页打开 market_view 后，快照数据为空，market_view 的快照模式要么报错要么静默回退到当前策略，结果与批次格不一致。

**建议**：
- 方案 A（推荐）：钻取按钮明确使用 `window.location.href` 同标签页跳转，并在 UI 上禁用右键/中键（或提示「请在当前标签页打开」）。如果用户确实需要新标签页，提供一个「复制钻取链接」按钮。
- 方案 B：改用 `localStorage`（跨标签页共享），但需处理清理（钻取完成后删除，避免残留）。
- 方案 C：钻取改为 POST 打开 market_view（form submit with hidden fields），不受存储限制。但跨页面 POST 比较 hacky。

**推荐方案 A**，实施最简单。在批次页明细表中，钻取行为设计为：
```js
// 单击行 = 同标签页跳转
row.addEventListener('click', () => {
    sessionStorage.setItem('batch_drill', JSON.stringify({...}));
    window.location.href = `/market-view?symbol=${symbol}&drill=1`;
});
```

### 2.2 🟡 market_view 快照模式的异常路径未覆盖

**问题**：§5.4 描述了快照模式的 happy path（sessionStorage 有数据 → 读取 → 自动运行），但未覆盖以下异常场景：

| 场景 | 当前设计覆盖？ |
|---|---|
| 用户直接在地址栏输入 `?drill=1`（无 sessionStorage） | ❌ |
| sessionStorage 数据格式错误或被篡改 | ❌ |
| 快照中的策略 JSON 校验失败（如缺少必需字段） | ❌ |
| 用户从批次页跳转后，在 market_view 刷新页面（sessionStorage 仍存在但 autorun 不应重复触发？） | ❌ |

**建议**：market_view 快照模式需实现以下防御：
1. 读不到 sessionStorage → 显示 toast「未找到批次快照数据，将使用当前策略回测」，回退到正常模式。
2. sessionStorage 数据校验失败 → toast「快照数据异常，已回退到当前策略」，清理 sessionStorage。
3. 读取成功后立即 `sessionStorage.removeItem('batch_drill')`（消费即销毁），避免刷新重复触发。如果担心用户刷新后丢失快照，可以在 URL 上加一个一次性 token，但 MVP 没必要。
4. `drill=1` 参数仅作为「尝试读取快照」的信号，非强制——读不到不报错。

### 2.3 🟡 data_version 漂移检测：可能过度告警

**问题**：§3.1 和 §5.1 中，`data_version = MAX(updated_at)` 来自 `market_data_qfq` 表。该表每天 16:30 增量更新后 `updated_at` 必然变化。这意味着**任何隔日钻取都会触发「数据已更新，结果可能漂移」提示**。

但实际上，如果钻取使用了锚定日期截断 bars，新增的日线数据不会影响钻取结果——真正的漂移来源只有历史数据修正（复权因子变化）。`MAX(updated_at)` 无法区分「新增一行」和「修改已有行」。

**影响**：用户频繁看到漂移警告 → 警告疲劳 → 真正有问题时不看。

**建议**：
- 方案 A：不做 `data_version` 检测，钻取结果页面始终标注「结果基于批次快照重跑，可能因历史数据修正产生轻微差异」（静态提示，非条件告警）。MVP 够用。
- 方案 B：`data_version` 改为 `SELECT MAX(updated_at) FROM market_data_qfq WHERE time <= anchor_date`。这样只检测锚定日之前的数据是否被修改过，新增的后续日线不会触发告警。但复权因子变化通常会更新所有历史行的 `updated_at`？需确认实际数据更新逻辑。
- 方案 C：钻取完成后对比 `excess_annual_return` 等关键指标与存储的 cell 值，偏差 > 阈值才告警。最精确但实现最复杂。

**推荐方案 A（MVP）+ 方案 C（V2）**。MVP 用静态提示替代动态告警，避免误报疲劳。

### 2.4 🟡 engine_version 实现路径模糊

**问题**：§3.1 和 §5.1 提到记录 `engine_version`（formula_version / git hash），但未明确取值方式和存储格式。从前两次代码核实看：

- `rule_backtest/indicators.py` 没有版本号机制
- 系统当前没有统一的「引擎版本」概念
- git hash 在运行时不可直接获取（需要部署时将 hash 写入文件）

**建议**：
- 方案 A：写一个简单的 `engine_version` 文件（部署脚本生成，如 `echo $(git rev-parse --short HEAD) > src/rule_backtest/ENGINE_VERSION`），batch_service 启动时读取。
- 方案 B：简化——`engine_version` 字段先建好但 MVP 填 `'1.0'`，后续再接入真实版本。
- 方案 C：干脆去掉 `engine_version` 字段，用 golden 测试锁定一致性，版本追溯靠 git blame。

**推荐方案 B**。预留字段零成本，MVP 填固定字符串即可，不为它拖慢实施。

### 2.5 🟢 symbol_features 表字段定义需精确化

**问题**：§5.1 特征表列定义中：

| 列名 | 当前说明 | 需澄清 |
|---|---|---|
| `momentum_250` | 近 250 日收益 | 是简单收益率（`close[-1]/close[-250]-1`）还是对数收益率？建议明确为「锚定日前 250 个交易日的价格收益率（close[-1]/close[-250] - 1），不足 250 日用全部可用数据」 |
| `amount_ma20` | 近 20 日均成交额 | 是最近 20 个交易日的 `amount` 简单平均，还是 `amount` 的 20 日均线末值？建议明确为 `SMA(amount, 20)` 在锚定日取值 |
| `trend_score_avg` | 近 250 日，param_set='default' | 是平均值、末值还是其他聚合？建议明确为「锚定日前 250 个交易日 trend_score 的均值」 |

实施时建议在 `batch_service.py` 的 `compute_features()` 函数中写清楚每个特征的计算公式（注释或 docstring），避免实现歧义。

### 2.6 🟢 策略快照中 `payload` 命名

**问题**：§5.1 批次表 `strategy_snapshot_json = [{id, name, payload}]`，§5.2 伪代码用 `strategy=strategy.payload`。`payload` 这个词过于通用，且与系统中其他概念（如 `registry_payload`）可能混淆。

**建议**：改为 `strategy_config` 或 `strategy_json`，语义更明确：
```json
[{ "id": "ma_cross", "name": "均线交叉", "strategy_config": { ... } }]
```

这是命名级别的建议，不阻塞实施。

### 2.7 🟢 批次并发控制缺少 hung 检测

**问题**：§5.3 规定「同时只允许一个 running 批次（重复发起 409）」。但如果 running 批次因某些原因卡死（引擎内部死循环、pandas 操作 hang 在超大数据上），cancel 是协作式的（§3.4.5），不会生效。此时用户无法发起新批次，也无法取消当前批次，陷入死锁。

**建议**：加一个轻量 watchdog：
- batch_service 记录 `last_cell_completed_at` 时间戳
- API `/progress` 返回该时间戳
- 前端检测：如果 `last_cell_completed_at` 超过 N 分钟（如 10 分钟）无变化，显示「批次可能卡死，请重启服务」并允许强制取消（直接标记 error）
- 或者更简单：提供一个 `?force=true` 的取消变体，跳过协作式检查，直接标记批次为 error

MVP 可以先不做（概率低），但设计文档应提及此风险。

## 四、补充提醒（实施注意事项）

### 4.1 data_anchor_date 的计算

§3.4.2：「批次启动锚定 `data_anchor_date = MAX(time)`（全库）」

核实：`market_data_qfq.time` 列为 TEXT 类型（非 DATE），但 SQLite 的 MAX 对 ISO 格式日期字符串（`YYYY-MM-DD`）能正确比较。如果 time 列含非日期前缀（如时间戳），MAX 可能不准确。**实施时需确认 time 格式为 `YYYY-MM-DD` 纯日期**。代码核实：`market_data_qfq` 主键为 `(symbol, time)`，time 应为日期字符串。

### 4.2 bars 截断的 pandas 写法

§5.2 伪代码：`bars = bars[bars.date <= anchor]`

注意：`bars` 是 `pd.DataFrame`（来自 `MarketStore.load_history()`），列名需要确认是 `date` 还是 `time`。从 `engine.py:36` 看是 `bars["date"]`（从 loader 已经重命名），但 `load_history()` 返回的原始列是 `time`（与 DB 列名一致）。**实施前确认 load_history 返回的列名**，如果原始列是 `time`，截断表达式应为 `bars = bars[bars["time"] <= anchor]`。

### 4.3 engine.run() 的 start_date 参数

§5.2 伪代码中 `start_date=None`，即使用标的完整历史。这是正确的（决策 #2：全生命周期）。但如果未来要支持「统一窗口」模式（如近 5 年），只需传 `start_date=...` 即可，设计上已预留。

### 4.4 单格 blob 端点 RESTful 路径中的特殊字符

§5.3：`GET /batch-backtest/api/runs/{batch_id}/cells/{symbol}/{strategy_id}`

symbol 可能含特殊字符（如数字开头的 ETF 代码 `510050`，无问题），但 strategy_id 可能含 `/`（极少但可能）。FastAPI 的路径参数默认不匹配 `/`。**建议 strategy_id 做 URL 编码**，或使用 query param 形式避免（如 `?symbol=X&strategy_id=Y`）。查询参数风格虽然不够 RESTful，但实现更可靠。当前设计两者都涉及，可以统一。

### 4.5 golden 测试的固定数据来源

§5.5 新增 `test_batch_golden.py`：「固定 symbol+固定区间+固定快照，锁定 summary 数值」

需明确：固定 bars 从哪里来？选项：
- 从真实数据库取（依赖 DB 状态，测试不稳定）
- 用 CSV fixture 存放固定行情数据（推荐，如 `tests/fixtures/golden_bars.csv`）
- mock `MarketStore.load_history()` 返回固定 DataFrame

推荐使用 CSV fixture，确保 golden 测试在任何环境下可复现。

- §2.1（sessionStorage 跨标签页）和 §2.2（快照模式异常路径）建议在实施 market_view 改造时一并处理，属于防御性编程，不增加多少工作量。

- 其余为实施细节提醒，可在编码阶段按需参考。

整体来看，v1.1 已经是一份可以放心交给实施的方案文档。修订记录的「采纳/不采纳+原因」格式值得作为后续方案迭代的标准模板。
