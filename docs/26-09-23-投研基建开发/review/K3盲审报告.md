## 2. 新发现 P1（实证详述）

### K3-P1-1 停牌日尾盘卖出崩溃：一条炸掉整个 run 的可达路径

**链路**（每一环都读码确认）：

1. `backtester.py:276` 卖出循环：`engine.sell(intent, ..., bar_close=_field_at(panel, t_idx, symbol, "close"), ...)`——标的当日无 bar（停牌）时 `_field_at` 返回 `None`；
2. `engine.py:120-122`：`fill_mode == "tail"` 且 `bar_close is None` → **直接 `raise ValueError("tail intent requires bar_close")`**——在调 matcher 之前；
3. `matcher.py:151-152` 的 `match_tail_sell` 明明有 `card.suspended → unfilled(suspended)` 分支（符合详设 §4.2「触发日停牌 → unfilled(suspended)，次日重试」），但从 engine 路径**永远不可达**（停牌 ⇒ 无 bar ⇒ bar_close=None ⇒ 先抛异常）——实质是死代码；
4. 异常上抛至日循环 try/except（backtester.py:311）→ `finish_run(failed)` → 实验 failed。**一次停牌废掉一次数分钟的完整 run**。

**可达触发面**（均为注册表内合法内置模块）：

- `time_stop`（position_risk.py:336-356）：`held >= max_days` 的判定**完全不查当日 bar**——持仓满 N 日那天恰停牌，必然触发；
- `ma_cross` 的 exit（signal.py:154）：停牌日 `close=NaN → above=False`，昨日 `above=True` → `cross_dn[t]=True` → 对持仓标的发 exit 事件；
- `abs_momentum`（signal.py:273-276）：持仓标的当日 mom=NaN → 不在 top_set → 发 exit；
- `buffered_rotation`（execution.py:84-106）：`_momentum` 对停牌标的取到最后有效值（stale），可能产出 rotation exit。

**实证**（只读探针，内存构造）：

```
Engine.sell(intent=ExitOrderIntent(fill_mode="tail", reason="time_stop"),
            card=TradabilityCard(suspended=True), bar_close=None, ...)
→ CRASH(ValueError): tail intent requires bar_close
```

**为何前审没抓到**：base-v1（`hard_stop` + `macd_cross use_exit:false`）不产生 tail 卖出
——hard_stop 的 `_triggered(bar=None)` 返回 False 不下意图，macd 不发 exit；
四轮审查的集成测试因此全部绕开此路径。现有测试无一覆盖「停牌日 tail 卖出」
（grep 证实 `bar_close=None` 只出现在 engine.py 的 raise 行）。

**修复指引**（供实施方，本审查不改代码）：engine.sell 的 tail 分支先查 `card.suspended`
（无 bar 时直接走 matcher 的 unfilled 语义），或把 `bar_close=None` 放行给 matcher 处理
（matcher 已有正确的 suspended 分支）；补一条「持仓停牌日命中 time_stop/ma_cross exit」
的集成钉子，断言 `unfilled(suspended)` 落账且 run 继续。

### K3-P1-2 holdout 放行机制端到端断线

详设 §6.6.4：「holdout 回测需显式放行 + 自动计数」；生效时点 = 阶段 5 起
（`holdout.is_enforced` 默认开，建设期测试显式关闭——已核实默认 `"1"`）。

当前实现的三段都在：**发放**（`holdout.grant_token`，human-only，web 有表单）、
**检查**（每个评估模块 runner 调 `check_window(..., token_id=ctx.get("holdout_token"))`）、
**消费**（原子 UPDATE 防 TOCTOU，有钉子）。**但没有任何通道把 token 递到 runner**：

- `worker.py:117`：`run_experiment(self.db, experiment_id, registry=self.registry)`——无 token；
- `research_tools.py:51`（MCP 同步路径）与 `research_cli.py:101`（CLI `--run`）：同样不传；
- `pipeline.run_experiment` 的 `holdout_token` 形参全库仅 recompute.py 显式传 `None`；
- web 表单 `/research-ledger/holdout/grant` 发放后 token 躺进表里，无人能消费。

后果：**enforced 开启后，任何窗口触碰 2025-01-01 之后的实验必然 failed**
（`HoldoutError → 工程失败入表`），用户发了 token 也没用——「人审放行」机制
名存实亡。`test_holdout_window_blocked_when_enforced` 钉住了拦截面，但没有
「token 放行后实验跑通」的端到端钉子（stage0 的 token 测试止步于 `check_window`
函数级）。

**修复指引**：token 绑定 experiment_id 发放后，worker/pipeline 在运行前查
「该实验的未消费 token」自动带出（或 CLI/MCP 增加 token 参数透传）；补
「发放→入队→跑通→token 已消费→holdout_touched 落账」的端到端钉子。

## 3. 新发现 P2（详述）

### K3-P2-1 涨跌停新股豁免的窗口计数 bug

`gateway/tradability.py:148-151`：`elapsed = searchsorted(trading_ordinals, day) −
searchsorted(trading_ordinals, listing_day)`——`trading_ordinals` 只含**请求窗口**内的
交易日。上市日早于窗口起点时第二项为 0，elapsed 退化为「窗口内第几天」：
**每次 run 的前 4 个交易日，所有「老股票」被误判为新股无涨跌停**（limit 价格 NaN →
is_limit_up/down 恒 False → 卡控失效）。

实证（上市日 2020-01-03，窗口 2024-03-01~08）：

```
2024-03-01  no_limit=True   limit_up=NaN     ← 误判
...
2024-03-07  no_limit=False  limit_up=11.0    ← 第 5 个窗口日起恢复正常
```

影响面：每个 run 窗口头 4 日的涨跌停卡控失效（该 4 日内涨停可买/跌停可卖）。
单次 run 占比小，但它是**确定性、每次必现**的口径错误，且直接打在 §3.2
（可交易性是全系统只在 L1.5 实现的一处语义）上。现有钉子
（`test_tradability_ipo_no_limit_window`、`test_ipo_no_limit_day5_vs_day6`）
都只覆盖「上市日在窗口内」。修复：elapsed 应按交易日历（或面板全轴）算，
不应限窗；补「上市日早于窗口」的钉子。

### K3-P2-2 事件多重性与事件日起算口径（event_study / bucket）

`event.py:179-191` / `bucket.py:153-166`：逐日调 `module.scan`，把每天返回的
entry 事件都计为一个独立事件。而信号模块的 entry 语义是**候选有效期**
（`macd_cross valid_days=5`：金叉后 5 个交易日内每天发候选）——于是一次金叉
产生最多 5 个「事件」，前瞻窗口高度重叠。后果：

- 名义事件数膨胀（`test_research_evaluations.py:90` 的锚点 2705 个事件即是
  40 只合成标的 × 候选期天数的产物），bootstrap 噪声带按事件级重抽、
  把高度相关的样本当独立样本 → **带偏窄，显著性被高估**；
- 前瞻收益从 scan 日（金叉后第 k 天）起算，而非事件日（金叉日）起算——
  测的是「金叉后第 0~4 天混合入场」的模糊口径，与假设文本（「金叉后 N 日」）
  不一致；
- `overlap_heavy` 警告（>0.3）大概率会亮，但警告不修正口径。

修复方向（二选一）：事件按 (symbol, 事件日) 去重并从前瞻起算点对齐；
或给信号模块加「事件模式」（只报边沿日）。补「同一金叉 5 天只算一次」的钉子。

### K3-P2-3 event_study 研究不了「跌破」：exit 事件被丢弃

`event.py:185-186`：`if ev.kind != "entry": continue`。信号模块的下穿语义
（`ma_cross use_exit` 的死叉、`trend_score_cross` 的下穿）都以 `kind="exit"`
发出——于是详设 §6.5.2 的招牌用例（`ma_touch@1(mode="cross_below")`、
「牛市跌破 MA20 的演绎」、卖方「N 次考验 MA20」类研究）经**信号模块双重身份**
路径产不出任何事件（0 事件 → inconclusive 进台账，正是 A-R2 修过的那种静默
形态换了个位置）。DSL 绕行可行（`cross_below(close, sma(close,20))` 的边沿是
entry），但没有任何文档/测试指明这条路。修复：event_study 支持
`event_side: entry|exit|both`，或事件定义模块化（详设 §6.5.2 本来设想的就是
独立事件定义）；补「exit 事件可研究」的钉子。

### K3-P2-4 进程停机留 running 孤儿（research_experiments + engine_runs）

`worker.stop()`（main.py lifespan 退出路径）只停调度线程与池，**在途 run 所在的
线程继续在裸奔**（`ThreadPoolExecutor.shutdown(wait=False)`）；进程真正退出后，
`research_experiments.status='running'` 与 `engine_runs.status='running'` 的行永挂。
启动补偿（`submit_all_queued`）只捡 `queued`；烂尾巡检（`list_stale_evaluating`）
只看 `evaluating`。**running 孤儿无人认领**。存量代码有现成惯例未沿用：
`mark_interrupted_batch_runs`（main.py:104）与 `mark_interrupted_at_startup`
（main.py:110）。修复：启动时把 running/evaluating 超龄的实验与 engine_runs
标记 failed/interrupted（台账口径：进程死亡 = 工程失败），补钉子。

### K3-P2-5 recompute_campaign 无通道

`research/recompute.py` 实现了 §6.6.7（批量复核 + supersedes 指针 + append-only），
单元/集成测试都在——但 `ResearchService` 无对应方法、MCP 11 工具不含、CLI 不含、
Web 不含。阶段 5 交付清单里的「recompute campaign」**实际无法被任何客户端触发**。
修复：服务面加 `recompute_campaign(old_ref, new_ref)`（human session 门）+ CLI
子命令；钉子已存在（`test_recompute_campaign`），只需通道层冒烟。

### K3-P2-6 recompute 复核 verdict 劫持 latest_verdict

`recompute.py:96-107` 给原实验追加新 verdict（final_verdict=NULL）。而
`verdict.latest_verdict` 按 id 取最新——复核后「最新」永远是那条不可确认的
复核 verdict（实验已 verdicted，`confirm_verdict` 要求 evaluating 态，新 verdict
永远落不了 final）。后果：`search_ledger(final_verdict="confirmed")` 漏掉被复核过的
confirmed 实验；详情页「最新 verdict」与 `/report.json` 默认展示复核稿而非定论；
`pipeline.run_status` 的 verdict 摘要同受影响。修复方向：latest_verdict 增加
「最新已确认」语义（或查询面优先取 final 非空行）；复核 verdict 的展示位与定论
分离。

### K3-P2-7 课题分级可平级翻转

`conclusion.py:22`：`GRADE_STRENGTH = {supported:2, refuted:2, mixed:1,
insufficient-evidence:0}`；`check_grade_allowed` 只做 `author ≤ suggested` 数值比较。
平台建议 `supported` 时作者写 `refuted` 照样放行（2≤2）——「可降不可升」的意图是
强度不升，但**方向翻转**（支持↔驳斥）不是降级。实验 verdict 的 VERDICT_RANK
（confirmed:2 > inconclusive:1 > rejected:0）没有这个问题（confirmed→rejected 被拦，
因为 0≤2 但方向语义不同——实际上实验侧 confirmed→rejected 也被允许！
VERDICT_RANK[rejected]=0 ≤ VERDICT_RANK[confirmed]=2 → 放行）。
两处共享同一个语义洞：强度序把「方向相反的结论」当成了「更弱的结论」。
修复：分级判定加「同向约束」——final 与 suggested 不同号（支持 vs 驳斥）时拒绝，
或显式要求额外 reasoning 门槛；补钉子。

### K3-P2-8 模块级 golden 测试缺口 + 报告缺件

**(a) §5.14 承诺落空**：「每个预置模块带 golden 测试与一句话文档」——文档

## 5. P3 清单（口径注记/小项，不阻断）

1. §5.4.1 骨架文字顺序为「rank → portfolio_risk → sizing」，实现为 sizing → gates
   （与 §5.2.5 `admit(intents)` 签名一致——gates 需要定量后的热增量）。文档内部
   不一致，实现选了可行口径；建议修订文档文字。
2. 创建型实验的对照只跑 buy-hold 一条（§6.1.4 写的是「benchmark 怀疑阶梯」），
   阶梯其余档位不进 evidence（报告层 benchmark_relative 也只有 base）。
3. `rank.by_freshness` 用日历日（`ctx.date − event_date`）而非交易日；排序键口径
   与模块语义（freshness=交易日龄）有细微差。
4. `reports.drawdown_durations`：水下天数按交易日计、修复天数按日历日计，混单位。
5. regime 段年化用算术口径（`mean×252`），主指标用几何口径——段间不可直接比。
6. `buffered_rotation` 的 `max_swaps` 参数已注册但实现恒为单次轮换（死参数）。
7. `MarketGate` 的 benchmark 不在面板标的集时静默失效（`_benchmark_below_ma` 返回
   None → 不触发、无警告）——配置错误无信号。
8. live 账户重建：`buy_date >= panel.dates[-1]` 判 sellable=0，盘后降级路径
   （面板末日=昨日）会把昨日买入错标不可卖——live 不撮合，无功能后果，口径注记。
9. live overlay 对每只标的 `load_market_data` 全历史仅为取 prev_vol（874 只全量
   读取）；14:05 每日一次可承，但属浪费型读法（LIMIT 1 即可）。
10. `engine_orders.status='pending'` 永不出现（订单只在终态落库）——schema 预留
    与实现形态不符，无实害。
11. 冻结是单向的：run 开始时**不等待**进行中的日更/指标重建（日更等 run，run 不
    等日更）；`force=True` 的启动补偿直接绕过冻结检查。面板在 run 头部一次性加载
    使实害窗口很小，但并发 run 的血缘 data_version 可能锚在重写中段。
12. `BoundGateway.get_panel` 不拦 `mode="live"`（模块可声明 live 模式）；无 overlay
    注入时无实害，信任模型内。
13. `PanelView.date_at(idx)` 不设上下界——模块可读到未来**日期**（交易日历信息，
    非行情）；评估为低风险。
14. python 模块白名单库内的 IO/网络能力（`np.load`、`pd.read_csv(url)` 等）不受
    AST 预筛约束——信任模型已声明「非对抗沙箱」，此处记录在案备查。
