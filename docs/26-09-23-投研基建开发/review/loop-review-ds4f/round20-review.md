### R20B-F1（P1）上游因子响应缺键/为空 → 本地因子表被整体清空 → qfq 全历史改写为不复权

- 位置：`src/data/provider_tickflow.py:331-346`（`raw_map` 非 dict 时取 `{}`；每个请求标的
  **无条件**写入 `factors_by_symbol[local_symbol] = factors`，缺键即空列表）
  → `src/data/service.py:417-418`（`factors_equal(stored, [])` 长度不等 → 判为"因子变更"
  → `db.replace_ex_factors(symbol, [])` 全量重写）→ 日更尾把它当**正常除权**走
  `repair_broken_symbols`（重物化 + 重建指标）。
- 事实（临时库副本 + 真实数据 002594.SZ + 真入口验证）：
  - 因子表 **12 条 → 0 条**；日志只有一句 `Ex-factor change detected … qfq rematerialization
    scheduled`（措辞是"正常除权"）；
  - qfq 重物化后 `335.739 → 111.003` = **−66.94% 单日断裂**（真实值 +0.37%），落在在用回测窗口内；
  - 指标重建**零 WARNING/ERROR**（完全静默）；
  - `compute_tradability` 真实输出：`2025-07-29 is_limit_down=True`（跌停价 303.30 vs 收盘 111.42）
    → **假跌停**：卖不出、止损顺延；因子完整时跌停价 99.91、无标记。
- 触发面：`ex_factors` 接口 50 标的/次，一次异常响应可清空整批（≤50 只）；若整响应非 dict，
  同批**所有**标的因子被清空。池内 **734/874** 只有因子（10,177 条）→ 随时可被整体改写；
  唯一"防线"是 vendor 下次正常响应时的 diff 恢复，期间**无任何校验**。
- **修复**：`sync_ex_factors` 加**清空守卫**——"上游返回空而本地有因子"时拒绝覆盖、保留本地因子、
  响亮告警（"因子消失不是正常公司行为"）。合法变更（新增/修改因子）照常落库（反向钉子）。

### R20A-F1（P2）我 R19 的 heat_cap 告警读错参数名 → 写出与配置矛盾的数字

- 我 R19 写的是 `params.get("cap")`，而该门的**声明参数是 `max_heat_pct`**（`cap` 是未声明参数，
  配置里写会被载入期拒绝）→ 该分支不可达、cap 恒为硬编码 6%。
- 实测：配置 `max_heat_pct=0.12` 时告警仍写 "cap=6.00%、111/242 天、5.35×cap"，
  按该 run 真实 cap 复算应为 **50/242 天、2.68×cap**。
- **修复**：抽 `heat_cap_of(config)` 读声明参数名；分母改为"可比行"（heat 有值且 equity>0）。
