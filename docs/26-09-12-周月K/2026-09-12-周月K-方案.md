# 周K / 月K 数据落库 设计方案

> 状态：**已落地**（2026-09-12 本地开发环境完成并全量补数验证；服务器部署见 §10）
> 日期：2026-09-12
> 需求来源：当前系统核心计算（标的查看、各类指标）全部基于日K，需要扩充周K/月K
> 三级数据。周/月 bar 一律取 **tickflow 接口**（已实测支持），不由本地日K聚合。

---

## 1. 目标与范围

### 1.1 要做

1. 数据库新增周/月K 存储（raw + qfq 两套口径，与日K 对齐）。
2. tickflow 拉取链路支持 `period`（1d/1w/1M），日K 既有行为完全不变。
3. 周/月K 的日更（随 16:30 盘后任务）+ 全量补数脚本。
4. 结构上支持后续「用周K 算趋势值 / 指标」——即任意指标计算可指定 `period`
   读取任意周期的行情，不需要再改表结构。

### 1.2 明确不做（本次）

| 不做的事 | 原因 |
|---|---|
| 周/月K 的指标缓存表（`indicator_weekly` 之类） | 本阶段只落「行情」；指标/趋势缓存等真正开始用周K 计算时再按需加，避免先落一堆空表。 |
| 看板/标的查看页的周月K 切换 | 本期目标是数据层，UI 视角是后续独立任务。 |
| 盘中实时合成周/月 bar | 与「盘中合成行永不落库」约定一致（见 §4.3）。 |
| 本地由日K 聚合出周/月K 作为真源 | 需求方明确要求用 vendor 接口；本地聚合仅作为**校验手段**（§8）。 |

## 2. 表结构设计

### 2.1 新增四张表

周期表与日K **逐列一致**，只是按周期分表：

| 表名 | 内容 |
|---|---|
| `market_data_raw_weekly` | 周K · 不复权（真源，追加型） |
| `market_data_qfq_weekly` | 周K · 前复权（vendor 直接给） |
| `market_data_raw_monthly` | 月K · 不复权 |
| `market_data_qfq_monthly` | 月K · 前复权 |

```sql
CREATE TABLE IF NOT EXISTS market_data_qfq_weekly (
    symbol TEXT NOT NULL,
    time TEXT NOT NULL,          -- bar 标注日（该周期内最后一个有成交的交易日）
    open REAL, high REAL, low REAL, close REAL,
    volume REAL, amount REAL,
    provider TEXT,
    updated_at TEXT DEFAULT (datetime('now','localtime')),
    PRIMARY KEY (symbol, time)
);
```

延用的既有约定：

- **`PRIMARY KEY (symbol, time)`** —— `time` 是文本 `'YYYY-MM-DD HH:MM:SS'`，
  与日K 同格式，所以 `ORDER BY time`、按日期区间比较、`substr(time,1,10)`
  等既有写法对周期表同样成立。
- **主键即索引**，不额外建索引（日K 侧 2026-08-25 已删掉同列冗余索引）。
- 表在 `Database._init_tables()` 里 `CREATE TABLE IF NOT EXISTS`，
  **服务器部署时会自动建表**，无需手工 DDL（见 §10）。

### 2.2 关键设计决策：为什么 qfq 周期表不能用「raw × 因子」本地物化

日K 的架构是 **raw 为唯一真源，qfq 由 `raw + 除权因子` 本地物化**
（`core/adjustment.py`）。周/月K **不能照搬**：

> 一根周 bar 内可能跨越除权日。除权日之前那几天的 OHLC 与之后那几天的 OHLC
> 用的复权因子不同，`open` 可能要用因子 A、`close` 要用因子 B —— 一根 bar
> 的四个价格各有各的因子，不存在「raw 周期 bar × 单一因子」的还原式。

所以：

- **`*_weekly_qfq` / `*_monthly_qfq` 直接存 vendor 的前复权结果**；
- 除权因子发生变化时，该标的的周期 qfq **整段重取**（`refresh=True` 路径），
  而不是本地重算；
- `*_weekly_raw` / `*_monthly_raw` 仍是不复权真源，除权不改写它 → 保持**追加型、
  不可变**（与日K raw 的语义一致）。

这一点写进了 `db.py` 建表注释和 `service.py` 的段落注释，避免后来者「顺手
统一成 raw→qfq 物化」而算错复权价。

### 2.3 `period` 维度如何接入既有访问层

所有 `market_data` 读写方法新增 `period` 关键字，**默认 `'1d'`**，既有调用方
零改动：

| 方法 | 变化 |
|---|---|
| `Database._market_table(price_mode, period)` | 表名解析：`market_data_{raw,qfq}[_{weekly,monthly}]` |
| `save_market_data` / `replace_market_data` | + `period` |
| `load_market_data` / `load_market_data_many` | + `period` |
| `get_market_data_summary` / `_many` / `list_market_data_summaries` | + `period` |
| `list_market_symbols` / `clear_market_data` / `count_bars_by_symbol` | + `period` |
| `market_data_version_name(symbol, price_mode, period)` | 版本名带周期：`market_data_raw_weekly:510300.SS` |
| `MarketStore(price_mode=..., period=...)` | 一个实例绑定一张周期表 |

表名后缀的构造是 `{base}_{period}`，所以 `price_mode` 仍是最后一段
（`market_data_raw_weekly`），与既有 `market_data_raw` / `market_data_qfq`
的命名方向一致。

> **`MarketStore.period` 是实例属性而非方法参数**：日/周/月各持一个实例
> （`_period_store(period, price_mode)`），调用方不必每次重复传周期。

## 3. 周期语义（`core/bars.py`，单一实现）

周期口径全部集中在 `core/bars.py`，db/provider/service 都调它 —— 与
「一个概念一份实现」的项目约定一致。

### 3.1 规范化

```python
normalize_period("1w") == normalize_period("weekly") == normalize_period("W") == "1w"
normalize_period(None) == "1d"
```

规范值**就是 vendor 的 period 取值**（`1d` / `1w` / `1M`），可直接透传给
tickflow。

**大小写是有意义的**：`1M` 是月线，`1m` 是分钟线。别名表刻意不收 `'m'`/`'1m'`，
误传分钟线直接 `ValueError`，绝不静默落成月K（有测试锁定）。

### 3.2 bar 标注日 = 该标的在本周期内最后一个有成交的交易日

这是本次最容易被忽略、也踩过坑的一点。vendor 的周期 bar **不是**按交易所
日历标注的，而是按**标的自身**的成交情况：

| 实例 | 周期 | 标注日 | 真实原因 |
|---|---|---|---|
| 万科A `000002.SZ` | 2015-12 月K | **12-18**（周四） | 12 月后半段停牌 |
| 招商银行 `600036.SS` | 2015-04 某周 | **04-02**（周四） | 定增停牌 |
| 万科A `000002.SZ` | 2017-06 某周 | **06-06**（周二） | 停牌 |
| 沪深300ETF | 2024-02-08 那周 | 02-08 | 春节休市，该周只有 4 个交易日 |

> **早期实现踩过的坑（已修正并有回归测试）**：第一版判据是「标注日的下一个
> 交易日是否跨周期」，结果把上表中**停牌导致的周中标注日**全部误判为「本周
> 还没走完」，直接丢弃 —— 万科A 一次丢了 2 根、招行 1 根。正确判据见 §3.3。

### 3.3 「未收盘周期不落库」判据

```python
is_period_bar_closed(bar_day, period) -> bool
```

判据只有一条：**该周期在今天的日历刻度上是否已经过去**（按周期标识比较，
不看相邻交易日）。

- 往期 bar → 一定已收盘（O(1)，不查日历）；
- 落在**当期**的 bar → 看本期最后一个交易日过没过：
  - 本期还有更晚的交易日 → 未收盘；
  - 今天就是本期最后一个交易日 → 需已过 15:00；
  - 今天是交易日但本期已无更晚交易日、且已收盘 → 已收盘；
  - 今天不是交易日、本期也无更晚交易日（假期中）→ 已收盘。

日线恒返回 `True`：日 bar 的落库节奏由既有日更流程决定，本次不改变日K行为。

### 3.4 落库过滤

`closed_bars(df, period, now=None)` 按上面判据过滤，**只保留已收盘周期**。

于是周/月表**永远不会出现「进行中的当周/当月」这种半截 bar** —— 与
CLAUDE.md 的硬约定「盘中合成行永不落库」（`intraday rows are never persisted`）
同源：盘中/期中数据只用于展示，不落库。

副作用（好的）：`*_raw_weekly` / `*_monthly_raw` 因此是**追加型**表，历史行
永不被回溯改写。

## 4. 拉取链路

### 4.1 provider（`data/provider_tickflow.py`）

```python
provider.fetch_history(symbol, start, end, adjust, period="1d") -> DataFrame
provider.fetch_histories(symbols, start, end, adjust, period="1d", *, batch_size, ...) -> (dict, errors)
```

- `period` 经 `normalize_period` 后透传给 `client.klines.get/batch`；
- **日K 包装方法保留**：`fetch_daily_history` / `fetch_daily_histories` 内部
  转调带 `period="1d"`，既有调用方与测试替身完全不受影响；
- 单标的路径的限流 key 仍是 `daily_kline_standard`，批量仍是 `daily_kline_batch`
  —— 周期不影响限流预算，vendor 的限流是按请求数而非周期算的。

实测（2026-09-12）：`1w` / `1M` 在 `get` 与 `batch` 两个接口都直接可用，
历史深度到 1991 年（万科A：周K 1774 根 / 月K 423 根），
**整段历史一次请求即可取回**（`count=10000` 装得下）。

窗口语义已验证：请求起点落在周期中间**不会**把该周期 bar 截断（周中请求
`2026-09-09~09-12` 与整周请求返回同一根 `2026-09-11` bar），所以窗口过滤
只按 bar 标注日做闭区间。

### 4.2 service（`data/service.py`）

核心入口：

```python
DataService.update_pool_periods(symbols, periods=("1w","1M"), *, start_date=None,
                                end_date=None, batch_size=100, max_retries=1, ...) -> dict
```

三个分支：

| 情形 | 起点 | 是否整段 |
|---|---|---|
| 首次入库（某侧表为空） | 1990-01-01（全历史）或显式 `start_date` | 整段 |
| 除权因子变化 | 该标的已有最早 bar | **qfq 整段**重取 |
| 常规日更 | 存量末根 bar 的**下一个周期的第一天** | 增量 |

**增量起点不能用「末根 + 1 天」**（`_period_fetch_start`）：周 bar 标在周五
（如 8-28），次日周六仍属同一周期，拿周六当窗口起点会把这一整根在途 bar 又
拉回来。正确做法是取「最早一个属于更晚周期的日期」，既排除末根自己，也排除
同周期的在途 bar；`not_before`（用户起点/全历史起点）是硬下限。

**默认首段起点取全历史而不是对齐日K起点**：整段历史也是一次请求，
而对齐日K（本地有 404 只标的日K只从 2020 起）只会把周/月K 白砍短。

**整段重取与增量分批隔离**：一只标的的整段重取不应该把同批其他标的的抓取
窗口也拉长（响应体积随窗口线性增长）。所以每轮把 `full` 与增量分成两组分别
成批。

**除权处理**：`update_pool_periods` 先 `sync_ex_factors` 拿到变化标的集合，
变化标的的 qfq 走整段重取；raw 仍走增量（除权不改写非复权价）。

**落库是 upsert 而非整表重写**：除权触发的整段重取会覆盖历史行，但落库失败
（网络中断）时**不会**把已有历史删成空表。

返回结构（按周期分组）：

```json
{"status": "...", "success": N, "failed": M, "failed_symbols": [...],
 "periods": {"1w": {"planned": .., "updated": .., "up_to_date": .., "failed": ..,
                    "rows_written": .., "dropped_open_period": .., "full_refetch": ..,
                    "coverage": {"start": "..", "end": ".."}, "results": [...]}}}
```

`dropped_open_period` 是「丢弃的未收盘 bar 根数」——正常日更里它就是
「本轮被过滤掉的在途周/月 bar」，可用来观察过滤是否生效。

### 4.3 日更集成（`core/jobs.py`）

16:30 盘后任务在日K 更新完成后追加一次 `update_pool_periods`：

- 结果放在日更 payload 的 `periods` 字段（**只留汇总，不带逐标的明细** ——
  日更行本身已记录全量 `results`，再叠一份会让 status 接口的 payload
  成倍膨胀）；
- 周/月K 同步**独立记 `job_runs`**（`job_type='period_update'`），失败不并入
  日K 的成功/失败计数，两边互不拖累；
- 任务内部异常被捕获并记入 `periods.error`，不会让日K 任务整体失败。

## 5. 全量补数脚本（服务器部署用）

```bash
# 全池（启用中的标的 + 基准指数），默认全历史、日更式增量
.venv/bin/python scripts/backfill_period_history.py

# 指定起点 / 只补某个周期 / 只补少数标的
.venv/bin/python scripts/backfill_period_history.py --start 1990-01-01
.venv/bin/python scripts/backfill_period_history.py --periods 1w
.venv/bin/python scripts/backfill_period_history.py --symbols 510300.SS,600036.SS

# 连 enabled=0 的标的也补
.venv/bin/python scripts/backfill_period_history.py --include-disabled
```

特性：

- **幂等**：`up_to_date` 的标的零写入、零额外请求（统计口径也有该分类），
  可反复执行；
- 走 `scripts/_common.py`（`.env` 加载 + DB 路径锚定项目根），从任意 cwd
  运行都指向同一个库；
- 日志：控制台 + `logs/ops/scripts.log`，逐标的明细带 `fetch_start` /
  `full` / 写入行数 / 本地覆盖区间，便于事后核对；
- 退出码：有失败标的返回 1（供部署脚本判断）。

| 表 | 行数 | 标的数 | 最早 bar | 最晚 bar |
|---|---|---|---|---|
| `market_data_raw_weekly` / `_qfq_weekly` | 574,173 | 874 | 1991-01-05 | 2026-09-11 |
| `market_data_raw_monthly` / `_qfq_monthly` | 136,086 | 874 | 1991-01-26 | 2026-08-31 |

全池补数结果（`scripts/backfill_period_history.py`，2026-09-12 本地）：

```
[1M] 计划 874 / 更新 871 / 已最新 3 / 失败 0；写入 271,346 行，
     丢弃未收盘 bar 1,746 根，整段重取 871 只
[1M] 覆盖区间：1991-01-30 ~ 2026-08-31
[1w] 计划 272 / 更新 271 / 已最新 603 / 失败 0；写入 413,310 行，
     丢弃未收盘 bar 0 根，整段重取 271 只
[1w] 覆盖区间：1991-01-05 ~ 2026-09-11
完成：874 只成功 / 0 只失败（状态 completed）
```

几处需要解释的数字：

- **月K丢弃 1,746 根** = 873 只 × 2（raw+qfq），即当时进行中的 2026-09 那根
  月 bar —— 这正是 §3.3 过滤生效的证据（9 月还没走完，不入库）。
- **周K丢弃 0 根**：补数当天是周六，本周已经收完，没有在途周 bar 可丢。
- **周K「已最新 603」** 来自中途用批量写代码重启后跳过已完成标的（幂等复跑），
  所以 `计划` 只有剩余的 272 只 —— 顺带验证了幂等性：已最新的标的零请求零写入。
- **池子是 874 只而不是日K的 875 只**：`551030.SS` 有 7 根日K但
  `instrument_metadata` 里没有它（不在标的池、且未启用），属于历史遗留行，
  补数脚本按设计只补「启用中的标的 + 基准指数」，故有意跳过。

## 8. 校验：vendor 周/月K vs 本地日K聚合

需求方选择「直接用 vendor 接口」，本节的目的是**独立验证 vendor 的周/月 bar
与本地日K自洽** —— 把本地日K（raw/qfq）按 ISO 周 / 自然月聚合
（open=首、high=max、low=min、close=末、volume/amount=sum），与库内周/月 bar
逐根比对。脚本：`scripts/verify_period_history.py`（部署后可直接复用）。

### 8.1 全量补数后的抽样结果：价格零差异

```
核对 80 只标的 × 周期 1w,1M × 口径 qfq
[1w] 一致 80 / 价格不一致 0 / 库内无周期数据 0 / 无日K 0
[1M] 一致 80 / 价格不一致 0 / 库内无周期数据 0 / 无日K 0
核对 80 只标的 × 周期 1w,1M × 口径 raw
[1w] 一致 80 / 价格不一致 0 / 库内无周期数据 0 / 无日K 0
[1M] 一致 80 / 价格不一致 0 / 库内无周期数据 0 / 无日K 0
```

即 80 只 × 2 周期 × 2 口径 = **320 组比对，open/high/low/close 全部一致**。

### 8.2 校验方法上的两个坑（都会伪装成「数据不一致」）

**坑一：本地日K的覆盖边界会产生半截周期。** 404 只标的的本地日K从
`2020-01-02`（周四）起，那一周本地只有 2 天，聚合出的 open/low 天然短于
vendor 按全周算的值 —— 首轮抽样 25 只里「6 只不一致」全部是这一条。校验脚本
因此固定丢掉每只标的的首尾两个周期。**这不是数据问题**，是校验方法的边界。

**坑二：本地日K的 amount 被四舍五入到百元。** 实测 `515630.SS`
2026-08-03：本地日库存 `28,515,700`，vendor 为 `28,515,743`。一周 5 天累计
偏差约 189 元（相对 1.1e-6），让「vendor 周K amount == 本地日K amount 求和」
在 1e-6 容差下失败。追查后确认 **vendor 侧完全自洽**：vendor 周K amount 与
vendor 日K amount 求和**逐位相等**（167,988,089.0 == 167,988,089.0），差异全在
本地日K的取整上。故校验脚本把求和量差异降级为「提示」、不判失败，价格才是
判定依据。

> 这两条都说明：抽样比对出现差异时，先确认是**校验方法**还是**数据**的问题，
> 不要直接归咎于新落库的数据。


### 8.3 除权标的：分红日附近的对齐需要单独确认（§2.2 的实证线索）

招商银行 600036.SH 2026-06 分红，看 2026-07-10 那根周 bar 的 `open`：

| 口径 | open |
|---|---|
| 用本地日K（已是前复权）聚合 | 36.81 |
| vendor `adjust=forward` | **35.72** |
| vendor `adjust=none` | 36.70 |

「本地日K 聚合」把已经做过前复权的日线再聚合，得到 36.81 —— 与 vendor 的
前复权周 open 差 1 元。这印证了 §2.2：**跨除权日的 bar 无法由本地还原，
必须直接取 vendor 前复权结果**；除权后该标的 qfq 整段重取。

### 8.4 停牌/假期 bar 不再被误丢

`is_period_bar_closed` 早期版本按「标注日 + 下一交易日是否跨周期」判断，会把
停牌导致的「标注日落在周期中间」的合法 bar 误判为进行中而丢弃（实测丢 4 根）。
现口径只看周期本身，四个实测日期已进回归用例（§6）。

## 11. 实施记录与偏差

1. **表名后缀方向**：实现取 `market_data_{raw,qfq}_{weekly,monthly}`
   （复权口径在末段），与日K 的 `market_data_raw` / `market_data_qfq` 同构词法。
   曾误写成 `market_data_weekly_raw`，与 `db._market_table()` 的拼接结果不符，
   已改正（本地库误建的两张表已清掉）。
2. **「未收盘周期」判据返工两次**，两个坑都来自「按交易日相邻关系推断周期」：
   - 首版用「标注日 + 下一交易日是否跨周期」→ 停牌把标注日拉到周期中间时误丢
     合法 bar（实测 4 根，见 §8.3）；
   - 第二版按「本期是否还有交易日」但把游标从今天算起 → 把「今天已是本期最后
     一个交易日」误判为进行中；
   最终口径与停牌/假期完全无关（§3.3），四个实测日期进回归用例。
3. **增量窗口起点不能取「末根 bar + 1 天」**：周 bar 标在周五，周六仍属同一
   周期，会把整根在途 bar 拉回窗口。改为 `_period_fetch_start()` 取「最早一个
   属于更晚周期的日期」（§4.2）。国庆周那根尤其反直觉：2025-09-30 的下一轮
   起点是 **2025-10-06**，不是 10-01。
4. **`fetch_histories` 的 provider 回退**：既有测试替身只实现了
   `fetch_daily_history/fetch_daily_histories`，新通用方法必须能在「通用接口
   缺失」时回退到日K旧接口（且不能多传 `period` 参数）；日K 的报错措辞
   （`TickFlow returned no daily history…` / `tickflow daily fetch failed…`）
   也保持不变，仅周/月K 报错带周期。回退分支由 `_accepts_period()` 判签名。
5. **日更 payload 只留汇总**：周/月K 的逐标的明细会随 400+ 标的膨胀，
   日更 payload 里只放 `periods.{1w,1M}` 的汇总字段，明细进
   `job_runs.period_update`（§4.3）。
6. **本地库里留下了全池周期数据（874 只，非需求要求）**：需求方原话是「当前仅
   本地开发环境，调通流程即可，之后要到服务器再部署一遍」。执行时把「调通流程」
   过度理解成了「跑一遍全池补数」，对 875 只标的做了全市场周K 抓取，被当面叫停
   （月K 抓到 703 只时停止）。**这批数据不是交付物**：它既没有坏处（日K读取路径
   `period` 默认 `1d`，本次改动不触及现有计算），也不构成服务器部署的前置条件。
   不需要时 `DROP TABLE` 四张周期表即可回到纯日K状态；服务器首次补数仍按 §10 执行。
   （后端流程本身已由小样本 + 交叉校验验证，见 §6/§8。）
7. **批量落库是补数过程中的性能返工**：首版 `_refresh_period_group` 逐标的
   调 `save_history`（每标的每口径各一次连接 + 独立事务），全池补数每批 100 只
   要几百次写事务，实测约 3 分钟/批。改为按批一次连接一次事务
   （`save_market_data_many` / `MarketStore.save_history_many`）后约 1.5 分钟/批；
   这条路径同时把**每晚日更**的写事务量从约 3500 次压到每批 2 次 —— 否则日更会
   平白多出几十分钟。批量写失败时回落逐标的写，坏标的不会牵连整批（有测试）。
   改动后周期测试 54 项全通过；全量套件随后补跑 = `1171 passed`（见 §6）。
8. **全量回归**：`1171 passed`（含周期开关与批量落库改动之后的全量补跑）；
   `test_instruments_bulk_backfill.py` 的 2 条失败为 Windows tempfile 权限既有
   flake，已在未改动的干净树上（`git stash` 后）复现同样失败。
9. **`551030.SS` 未补周K是有意为之**：它有 7 根日K但 `instrument_metadata`

## 13. 两个待决问题的研究结论（仅分析，未改代码）

### 13.1 副图数据从哪来？切周期要不要重算？（对应提问 #2）

**先纠正一个前提**：标的查看页的副图**不是**从数据库读现成的。`indicator_daily`
/ `trend_daily` 这两张缓存表**只服务**：

- `services/dashboard.py` —— 标的大盘/热力图/相位列；
- `services/stop_loss.py` —— 止损线（ATR 序列）。

标的查看页走的是**实时现算**：`build_market_payload()` 里
`compute_market_indicators(data, ...)` 直接对刚读出的 OHLCV DataFrame 算全套
指标（`core/indicators.py` + `core/trend.py`）。所以「之前日K的副图数据都存在
数据库里、没有现算逻辑」这个印象与实际不符 —— 详情页从来都是现算的。

由此得出两条结论：

1. **切周期不需要任何新表、也不需要「重算」缓存**：副图既然是「喂什么 K 线
   算什么」，把周/月 OHLCV 喂进同一个函数就得到周/月副图（本次实现即如此）。
2. **也没有「因为周月K没保存所以只能重算」的问题**：周/月K 已经落库（§2、
   §7），详情页读它们与读日K是同一条路径。

真正受影响的不是「能不能算」，而是**参数语义**（见 13.2）。

### 13.2 趋势值公式能否等价迁移到周/月K？（对应提问 #3）

**能跑，代码一行都不用改；但不能算「等价」。**

代码层面：`calculate_trend_score_series(bars, cfg)` 只吃 OHLCV，公式内部
全部是**无量纲**量 —— `bias=(C-MA_n)/ATR`、`slope=ΔEMA_n/(ATR·n)`、再经
`tanh` 压缩到 [-1,1]，ATR 同时出现在分子分母的尺度归一里。所以它对「bar 是
日还是周/月」没有假设，喂周K 即得周线趋势值（本次页面切换已经在用）。

语义层面有三处必须知道的变化：

| # | 变化 | 说明 | 实测 |
|---|---|---|---|
| 1 | **参数是「根数」** | `n_short=3/n_mid=5/n_long=8/atr_period=20/er_period=10/vol_ma_period=20` 全部按 bar 计数。日K 上是 3/5/8 日、ATR20≈1个月；周K 上是 3/5/8 **周**、ATR20≈**4.6个月**；月K 上是 20 **个月**≈1.7年 | 同一标的 MA20：日K 4.658 / 周K 4.780 / 月K 4.377 |
| 2 | **tanh 输入尺度漂移** | 月K 的 `bias_mix` 均值明显大于日K（长周期里价格偏离 MA8 更远、而 ATR20 平滑），tanh 更容易进入饱和区 | `bias_mix` 均值 510300.SS：日 0.047 → 月 0.123；600036.SS：日 0.025 → 月 0.218（约 4~9 倍） |
| 3 | **预热门槛按根数** | `_min_bars = max(n_long, atr_period)+2 = 22` 根。月K 上意味着**上市后约 22 个月才出第一个趋势值** | 510300.SS 月K 140 根（2015-01-30 起），首个有效趋势值出现在 **2016-10-31** |

另外两处「同一个常数在周/月K 上换了含义」：

- **`vol_ratio/3.0`（confidence 的成交量项）**：3.0 这个饱和常数是日成交量
  标定的。周/月成交量是区间求和，波动被平均掉、分布更窄，同一常数会改变
  confidence 的整体水位（实测 confidence 均值在 0.29~0.36 间小幅移动，尚可
  接受，但并非不变）。
- **`趋势相位` 的 ±5 阈值与 MA5**：`_detect_trend_phase` 的 `ts>=5 and ma5>=0`
  阈值、以及 `MA5`（5 根，日K 上是 5 天、周K 是 5 周）同样是从日K 标定的；
  相位字段 `days` 的语义在周/月K 上应读作「周数/月数」。

**结论与建议（未实施）**：

1. 若只想「看」，现状即可用 —— 同一个公式换 K 线，读数自成一体；
2. 若要让周/月趋势值与日K 的**经济含义对齐**（例如都表达「约 1 个月的结构」），
   需按 bar 换算参数：周K 约 ÷5、月K 约 ÷21。但日线的 3/5/8 **无法**在周线上
   表达（3 日 ≈ 0.6 周，低于 1 根 bar 的分辨率），所以周线只能用 1/2/3 这类
   更粗的档位，本质上是**换了一套指标**而不是「等价迁移」；
3. 若要用周/月趋势值做**信号/阈值判定**（相位、告警、回测），必须先在周/月K 上
   重新标定 ±5 阈值与 MA5 口径 —— 现有阈值只在日K 上验证过；
4. 指标缓存表（`indicator_daily`/`trend_daily`）目前无 `period` 列。将来若要
   缓存周/月指标，按 §9 的建议加 `indicator_weekly`/`trend_weekly`（含
   `period`/`formula_version`/`data_version`），`data_version` 复用带周期的
   命名即可接上现有陈旧检测。**本次不需要动**。
